IChat Templates

IChat Templates

Three representations of the same conversation, each one step closer to what the model actually sees.

aMessage List

The API format. Structured, readable, model-agnostic. This is what your env writes, what the verifier sends to vLLM.

json 
[
  {"role": "system", "content": "You are a helpful assistant."},
  {"role": "user", "content": "What is the capital of France?"},
  {"role": "assistant", "content": "Paris."},
  {"role": "user", "content": "And Germany?"},
  {"role": "assistant", "content": "Berlin."}
]

bTemplate-Rendered String

The tokenizer applies a Jinja template (stored in tokenizer_config.json on HuggingFace) and produces a raw string. Every model family has a different template. Qwen uses ChatML:

chatml 
<|im_start|>system
You are a helpful assistant.<|im_end|>
<|im_start|>user
What is the capital of France?<|im_end|>
<|im_start|>assistant
Paris.<|im_end|>
<|im_start|>user
And Germany?<|im_end|>
<|im_start|>assistant
Berlin.<|im_end|>

Same message list, completely different string per model family. Feed a model the wrong template format and it still runs — it just performs worse because the token patterns are unfamiliar.

cToken IDs

The rendered string gets tokenized into integer IDs. This is the only thing that enters the model.

tokens 
[151644, 8948, 198, 2610, 5765, ..., 151645, 198, 151644, 872, 198, ...]

Delimiter strings like <|im_start|> are single tokens: <|im_start|> is token 151644 in Qwen, not a sequence of characters. The tokenizer has them in its vocabulary as special tokens. The model outputs logits over this same vocabulary at each position.

dWhy This Matters for Training

During generation, vLLM handles all three steps internally. You send message lists, it applies the template, tokenizes, generates, returns text.

During training, the orchestrator reconstructs the exact same token sequence that vLLM generated — the full multi-turn conversation as one flat array of token IDs. It does this to:

What Why
loss mask 0 for prompt/system/user/special tokens, 1 for assistant completion tokens
sampling logprobs Align logprobs from vLLM generation time with the correct positions
trainer logprobs Compute on the same sequence for the policy ratio

If the trainer's tokenizer applies the template differently from vLLM's — even one extra newline or a missing BOS token — the token IDs shift and the logprobs are misaligned. The loss is computed on wrong positions. No error, just bad gradients.

In practice this doesn't happen: both vLLM and the trainer load the same model from HuggingFace, same tokenizer_config.json, same Jinja template, same tokenization. They agree automatically.

eMulti-Turn Masking

For single-turn, the flat sequence is prompt tokens then completion tokens. Simple mask. For multi-turn, the full conversation is one array:

mask 
[system] [user: question₁] [assistant: answer₁] [user: question₂] [assistant: answer₂]
   0           0                    1                   0                    1

All processed left-to-right in one forward pass during training. The orchestrator finds where each assistant turn starts and ends by applying the same template and locating the boundaries. If the boundaries are off by even one token, you're training on user tokens or skipping completion tokens.

During generation it's incremental: vLLM generates turn 1, the env injects the follow-up, vLLM generates turn 2 with the full history. During training, the entire conversation is one sequence in a single forward pass.
