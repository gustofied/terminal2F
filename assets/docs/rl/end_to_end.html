PRIME & VERIFIERS

IPieces

Three things to train: a model, an environment, and a trainer. The environment lives in verifiers. The trainer can be anything – verifiers-rl, prime-rl, SkyRL, rLLM, your own. It just needs to call env.generate() and consume the rollouts.

Piece What
model HuggingFace model ID. Loaded into vLLM for inference and into transformers/deepspeed for training. Same weights, two copies.
environment A verifiers environment: dataset + reward functions + conversation loop. Versioned Python package – importable, reproducible, pinned with deps.
trainer Orchestrates rollouts, computes advantages, runs the training loop, syncs weights back to vLLM. Verifiers-rl and prime-rl are the two we use, but any trainer that speaks the same protocol works.

You need at least two GPUs on one node: one for inference (vLLM), one for training. They share weights via NCCL over the PCIe/NVLink bus inside the same machine. Multi-node (2+ machines) adds networking complexity and is only worth it when you need to scale.

IIEnvironment Setup

Environments are versioned Python packages – importable, reproducible, pinned with deps.

Consumer mode – install and use, can't edit:

prime env install owner/env-name

Goes into site-packages. Meant for running, not editing.

Developer mode – pull source, install editable, hack on it:

prime env pull owner/env-name@latest --target ./environments/env-name
uv add --editable ./environments/env-name

Source is in your tree. Changes take effect immediately.

aPreferred Workflow

Always pull + editable. Never blind install.

Why: you always want to see what you're running. Editable installs mean you can read and modify the environment code directly, debug reward functions, tweak prompts – without reinstalling anything. When something breaks during training you can trace it right to the source. Blind installs hide the code in site-packages where you'll never look at it.

# 1. Pull the source
prime env pull owner/env-name@latest --target ./environments/env-name

# 2. Make it editable in your project (recorded in pyproject.toml)
uv add --editable ./environments/env-name

# 3. Hack on it, run eval, iterate
vf-eval configs/eval.toml -e configs/endpoints.toml

# 4. Push changes back
prime env push --auto-bump   # auto-bumps version in pyproject.toml

bQuick vs Recorded Install

Command What it does In pyproject.toml?
uv pip install -e ./path Editable install into venv No – uv sync can forget it
uv add --editable ./path Editable install + writes path dependency Yes – stays part of project

Use uv add --editable when you want it to persist. Use uv pip install -e for quick throwaway testing.

cCreating a New Environment

# Scaffold files (does NOT make it importable)
prime env init my-env --path ./environments/my-env

# Make it importable
uv add --editable ./environments/my-env

prime env init only creates files. You still need the editable install for Python to find it.

IIINode Setup

Manual setup on a remote GPU node with verifiers-rl. Not the golden path – the hands-on way to understand what's happening.

aSSH keys

Generate a dedicated keypair on your machine:

ssh-keygen -t ed25519 -a 64 -f ~/.ssh/primeintellect_ed25519 -C "primeintellect"

Copy the public key (cat ~/.ssh/primeintellect_ed25519.pub), paste it in the provider dashboard, deploy a 2-GPU instance.

To avoid passing -i every time:

eval "$(ssh-agent -s)"
ssh-add --apple-use-keychain ~/.ssh/primeintellect_ed25519

bSSH and workspace

ssh -i ~/.ssh/primeintellect_ed25519 -p <port> root@<ip>
nvidia-smi                     # should show GPU 0 and GPU 1

cd /workspace
mkdir -p rl-tutorial && cd rl-tutorial

cInstall uv and create venv

curl -LsSf https://astral.sh/uv/install.sh | sh
source $HOME/.local/bin/env
uv venv --python 3.12
source .venv/bin/activate

dUpload local files

From your local machine, not the node:

# verifiers-rl package
scp -P <port> -i ~/.ssh/primeintellect_ed25519 -r \
  ~/projects/terminal2F/external/verifiers/packages/verifiers-rl \
  root@<ip>:/workspace/rl-tutorial/verifiers-rl

# environment
scp -P <port> -i ~/.ssh/primeintellect_ed25519 -r \
  ~/projects/terminal2F/environments/alphabet-sort \
  root@<ip>:/workspace/rl-tutorial/alphabet-sort

Why scp instead of pip install? verifiers-rl lives inside the verifiers monorepo under packages/verifiers-rl/ – it's not on PyPI as a standalone package. And the environment was local/unpublished, not yet on the hub. If both were published you'd skip scp entirely and just install on the node.

eInstall verifiers-rl

Do NOT use --no-deps. This installs everything: vllm, flash-attn (compiles from source, ~15 min), deepspeed, liger-kernel, trl, accelerate, torch.

cd /workspace/rl-tutorial
uv pip install ./verifiers-rl

Do NOT start vLLM during this step. flash-attn compilation eats RAM. If vLLM is running too, the node can OOM and crash.

# If flash-attn OOM's during compile even without vLLM:
MAX_JOBS=4 uv pip install ./verifiers-rl

fInstall extras

uv pip install wandb
uv pip install -e ./alphabet-sort

gStart vf-vllm on GPU 0

export HF_TOKEN=your_token
CUDA_VISIBLE_DEVICES=0 vf-vllm --model willcb/Qwen3-0.6B \
  --enforce-eager --disable-log-requests

Wait for Application startup complete.

Why vf-vllm not vllm serve? Training needs weight sync. After each step the trainer pushes updated weights from GPU 1 to GPU 0 via NCCL. vf-vllm adds /init_communicator, /update_weights, /get_world_size endpoints. Regular vllm serve gives 404 on those.

hRun training on GPU 1

In a second tmux pane:

cd /workspace/rl-tutorial && source .venv/bin/activate
export HF_TOKEN=your_token
export WANDB_API_KEY=your_key
CUDA_VISIBLE_DEVICES=1 vf-rl @ configs/train.toml

iCommon errors

Problem Fix
flash-attn OOM during install Kill vLLM first, or MAX_JOBS=4
vf-vllm: command not found source .venv/bin/activate
404 on /get_world_size Used vllm serve instead of vf-vllm
401 Unauthorized on HF Hub export HF_TOKEN=xxx
NCCL error after Ctrl+C Restart both vf-vllm and training
SSH disconnect kills training Use tmux
CUDA OOM on backward pass Reduce micro_batch_size (4 instead of 8)
/workspace is slow or missing Network mount on some providers. Local disk is /
prime can't find verifiers uv tool envs are isolated. Use one project venv instead

IVTrainer

We use a TOML config. verifiers-rl is part of the verifiers monorepo.

aConfig

configs/vf-rl/alphabet-sort.toml 
model = "Qwen/Qwen3-4B-Instruct-2507"

[env]
id = "kalomaze/alphabet-sort"

[env.args]
min_turns = 3
max_turns = 5

[inference]
gpus = 1

[inference.args]
enforce_eager = true

[trainer]
gpus = 1

[trainer.args]
run_name = "alphabet-sort"
micro_batch_size = 16
rollouts_per_example = 16
batch_size = 512
max_steps = 100
max_tokens = 512
max_seq_len = 1024

Top-level model applies to both inference and trainer. GPU counts are split sequentially: inference gets GPU 0, trainer gets GPU 1.

bWhat happens

Step
1 vf-vllm loads model into GPU 0, starts serving
2 vf-train loads model into GPU 1, connects to vLLM, initializes NCCL
3 Orchestrator calls env.generate() – verifiers drives the conversation loop, vLLM generates completions
4 Rollouts scored by rubric, advantages computed, microbatches packaged
5 Trainer forward pass, loss, backprop, optimizer step
6 NCCL weight sync: GPU 1 → GPU 0
7 Back to 3 with updated weights
