IPieces

When working with verifiers and Prime, there are three pieces to deal with: a model, an environment, and a trainer. The environment lives in verifiers, which builds all the machinery around it: state management, the multi-turn conversation loop, trajectory tracking, rubric scoring. The trainer can be anything: verifiers-rl, prime-rl, SkyRL, rLLM, your own. The connection point is env.generate() on the environment instance. The trainer calls it, verifiers drives the rollouts, and scored trajectories come back.

Piece What
model HuggingFace model ID. Loaded into vLLM for inference and into transformers/deepspeed for training. Same weights, two copies.
environment A verifiers environment: dataset + reward functions + conversation loop. Versioned Python package, importable, reproducible, pinned with deps.
trainer Orchestrates rollouts, computes advantages, runs the training loop, syncs weights back to vLLM. Verifiers-rl and prime-rl are the main two, but any trainer that speaks the same protocol works.

You need at least two GPUs on one node: one for inference (vLLM), one for training. They share weights via NCCL over the PCIe/NVLink bus inside the same machine. Multi-node (2+ machines) adds networking complexity and is only worth it when you need to scale.

IIEnvironment Setup

Environments are versioned Python packages. Importable, reproducible, pinned with deps.

Consumer mode (install and use, can't edit):

shell 
prime env install owner/env-name

Goes into site-packages. Meant for running, not editing.

Developer mode (pull source, install editable, hack on it):

shell 
prime env pull owner/env-name@latest --target ./environments/env-name
uv add --editable ./environments/env-name

Source is in your tree. Changes take effect immediately.

aPreferred Workflow

Always pull + editable. Never blind install.

Why: you always want to see what you're running. Editable installs mean you can read and modify the environment code directly, debug reward functions, tweak prompts, without reinstalling anything. When something breaks during training you can trace it right to the source. Blind installs hide the code in site-packages where you'll never look at it.

shell 
# 1. Pull the source
prime env pull owner/env-name@latest --target ./environments/env-name

# 2. Make it editable in your project (recorded in pyproject.toml)
uv add --editable ./environments/env-name

# 3. Run eval against any OpenAI-compatible model
prime eval run my-env -m openai/gpt-4.1-mini -n 10

# 4. View results in the browser (live-reloads on refresh)
t2f eval view

# 5. Iterate, then push changes back
prime env push --auto-bump

prime eval run saves results to outputs/evals/{env}--{model}/{run_id}/. Evaluations use Prime Inference by default; configure your own API endpoints in ./configs/endpoints.toml. t2f eval view starts a local server that reads those results and renders them. Refreshing the browser re-reads the files, so you always see the latest data.

bQuick vs Recorded Install

Command What it does In pyproject.toml?
uv pip install -e ./path Editable install into venv No, uv sync can forget it
uv add --editable ./path Editable install + writes path dependency Yes, stays part of project

Use uv add --editable when you want it to persist. Use uv pip install -e for quick throwaway testing.

cCreating a New Environment

shell 
# Scaffold files (does NOT make it importable)
prime env init my-env --path ./environments/my-env

# Make it importable
uv add --editable ./environments/my-env

prime env init only creates files. You still need the editable install for Python to find it.

IIIEval on Remote

Setting up a remote GPU node properly: vLLM serving, environment install, and running evals against a local model endpoint. This is the same setup used for training, just without the trainer. Getting this right first means training is just one more step.

aSSH in

With the SSH agent already loaded (see section IV.a), connect to the node:

shell 
ssh -i ~/.ssh/primeintellect_ed25519 -p <port> root@<ip>

You land in /root/, the root user's home directory. This is ephemeral. All work goes in /workspace/, which is persistent storage mounted by the provider.

shell 
cd /workspace
mkdir -p <project> && cd <project>

bInstall uv, tmux, and create venv

shell 
# tmux keeps processes alive when SSH drops
apt-get update && apt-get install -y tmux

curl -LsSf https://astral.sh/uv/install.sh | sh
export PATH="$HOME/.local/bin:$PATH"
uv venv
source .venv/bin/activate

Optionally, scp a tmux config to make the remote tmux more comfortable (mouse scrolling, ctrl+a prefix so it does not conflict with local tmux):

shell (local) 
scp -P <port> -i ~/.ssh/primeintellect_ed25519 \
  ~/projects/terminal2F/configs/remote/.tmux.conf \
  root@<ip>:~/.tmux.conf

cInstall vLLM

The install command depends on the CUDA version on the node (nvidia-smi top right). Check vllm.ai for the latest wheels. For CUDA 13.0:

shell 
uv pip install vllm \
  --extra-index-url https://wheels.vllm.ai/0.16.0/cu130 \
  --extra-index-url https://download.pytorch.org/whl/cu130 \
  --index-strategy unsafe-best-match

dServe the model

shell 
# base model (no fine-tuning)
vllm serve <model-id> --enforce-eager

# if trained with LoRA: serve base model + adapter
vllm serve <base-model-id> --enforce-eager \
  --enable-lora \
  --lora-modules trained=<adapter-hub-id>

# merged model or local path: use --served-model-name for a clean label
vllm serve /path/to/merged-model --enforce-eager \
  --served-model-name <clean-name>

Starts an OpenAI-compatible API on http://localhost:8000. Wait for Application startup complete before running evals. --enforce-eager skips Triton graph compilation, which can fail on newer CUDA versions (13.0+). Slightly slower inference but avoids setup headaches.

--served-model-name controls the model ID that vLLM registers. Without it, vLLM uses the path or HuggingFace ID, which can be ugly (e.g. /workspace/emaileval/merged-model). The -m flag in prime eval run must match this name — it is both the label on the eval dashboard and the model ID sent to vLLM. So always set a clean name when serving local paths.

LoRA adapters are small patches (~3MB) on top of a frozen base model. They cannot be served on their own — vLLM loads the full base model first, then applies the adapter. The --lora-modules flag gives the adapted model a name (trained) that you use as the model ID in eval. To avoid the LoRA flags entirely, you can merge the adapter into the base model and serve as a standalone model.

eRun eval

In a second tmux pane, activate the same venv and install prime + the environment:

shell 
cd /workspace/<project> && source .venv/bin/activate

uv pip install prime
prime env install <env-id>

Point the eval at the local vLLM endpoint with --api-base-url and --api-key-var. The -m flag is both the model ID sent to vLLM and the label on the eval dashboard — it must match --served-model-name if you set one.

shell 
export VLLM_API_KEY=empty

prime eval run <env-id> -m <model-name> -n 10 -r 3 \
  --api-base-url http://localhost:8000/v1 \
  --api-key-var VLLM_API_KEY

--api-key-var is the name of an env var, not the key itself. vLLM does not need auth, so any dummy value works. Short flags: -b for --api-base-url, -k for --api-key-var.

IVTraining

Manual setup on a remote GPU node with t2f-trainer. Not the golden path, but the hands-on way to understand what's happening.

verifiers-rl is the optional RL trainer inside the verifiers monorepo (packages/verifiers-rl/). Not actively maintained, but intentionally lightweight and readable, good for experimentation and education. t2f-trainer is a fork of it, extracted into its own package. That's what the rest of this section uses.

aSSH keys

Generate a dedicated keypair on your machine:

shell 
ssh-keygen -t ed25519 -a 64 -f ~/.ssh/primeintellect_ed25519 -C "primeintellect"

Copy the public key (cat ~/.ssh/primeintellect_ed25519.pub), paste it in the provider dashboard, deploy a 2-GPU instance.

To avoid passing -i every time:

shell 
eval "$(ssh-agent -s)"
ssh-add --apple-use-keychain ~/.ssh/primeintellect_ed25519

bSSH and workspace

shell 
ssh -i ~/.ssh/primeintellect_ed25519 -p <port> root@<ip>
nvidia-smi                     # should show GPU 0 and GPU 1

cd /workspace
mkdir -p <project> && cd <project>

cInstall uv and create venv

shell 
curl -LsSf https://astral.sh/uv/install.sh | sh
export PATH="$HOME/.local/bin:$PATH"
uv venv
source .venv/bin/activate

dUpload local files

From your local machine, not the node:

shell 
# t2f-trainer package
scp -P <port> -i ~/.ssh/primeintellect_ed25519 -r \
  ~/projects/terminal2F/external/t2f-trainer \
  root@<ip>:/workspace/<project>/t2f-trainer

# environment
scp -P <port> -i ~/.ssh/primeintellect_ed25519 -r \
  ~/projects/terminal2F/environments/<env-name> \
  root@<ip>:/workspace/<project>/<env-name>

Why scp? t2f-trainer is a local package, not on PyPI. The environment is also local/unpublished. If both were published you'd skip scp and just install on the node.

eInstall t2f-trainer

This pulls in the full training stack: vllm, deepspeed, liger-kernel, trl, accelerate, torch, wandb. The golden path:

shell 
cd /workspace/<project>
uv pip install hatchling
uv pip install ./t2f-trainer --no-build-isolation

# pin versions that break otherwise (see reasoning below)
uv pip install 'transformers>=4.45,<5' 'verifiers==0.1.10'

Why each of these:

hatchling is the build backend t2f-trainer uses (declared in its pyproject.toml). With --no-build-isolation, uv does not auto-install build tools into a temporary environment, so hatchling must already be in the venv.

--no-build-isolation tells uv to build packages using what is already installed in the venv rather than creating an isolated build environment. This is needed because flash-attn (if enabled) requires torch headers at compile time, and an isolated build env would not have torch. Even without flash-attn, --no-build-isolation avoids edge cases where the build backend is missing.

transformers>=4.45,<5 because vLLM 0.10.x calls tokenizer.all_special_tokens_extended, which was removed in transformers 5.x. Without this pin, vLLM crashes on startup. The t2f-trainer install pulls in transformers 5.x by default, so the pin must come after.

verifiers==0.1.10 because 0.1.11 changed resolve_client() and rejects the AsyncOpenAI client that the orchestrator originally passed. t2f-trainer has been updated to use ClientConfig instead, which should work with 0.1.11+. If you are using the updated t2f-trainer, try dropping this pin. If rollouts fail with ValueError: Unsupported client type, add it back.

flash-attn is commented out in t2f-trainer's pyproject.toml by default. It is a CUDA C++ library that compiles from source against your exact torch + CUDA versions (~15 min). For small models with enforce_eager = true, it is not needed. For larger models it matters — 2-3x faster attention, O(n) memory instead of O(n²).

If you need flash-attn, the cleanest path is to grab a pre-built wheel from Dao-AILab's releases that matches your torch + CUDA version. If a matching wheel exists, install is instant. If not, you fall back to source compilation:

shell 
# option 1: pre-built wheel (check releases for your torch + CUDA)
uv pip install flash-attn

# option 2: compile from source (~15 min)
MAX_JOBS=4 uv pip install flash-attn --no-build-isolation

Using a Docker image (NVIDIA NGC, RunPod templates) that comes with flash-attn pre-installed avoids this entirely. TODO: check if matching a specific torch version to available flash-attn wheels is a faster path than compiling.

fInstall extras

shell 
# editable install so local env changes take effect immediately
uv pip install editables
uv pip install -e ./<env-name>

# tokens for wandb and HF
export WANDB_API_KEY=your_wandb_key
export HF_TOKEN=your_write_token

editables is needed for -e (editable) installs with --no-build-isolation. The HF token needs write access if using push_to_hub.

gConfig

configs/t2f-rl/<env-name>.toml 
model = "<model-id>"

[env]
id = "<env-id>"

[env.args]
# environment-specific arguments

[inference]
gpus = 1

[inference.args]
enforce_eager = true

[trainer]
gpus = 1

[trainer.args]
vllm_server_host = "127.0.0.1"
run_name = "<run-name>"
micro_batch_size = 4           # 16 OOMs on A6000 48GB
rollouts_per_example = 16
batch_size = 512
max_steps = 100
max_tokens = 512
max_seq_len = 1024
learning_rate = 1e-5
use_lora = true
save_strategy = "steps"
save_steps = 25
save_only_model = true
push_to_hub = true
hub_model_id = "<your-org>/<model-name>"

Top-level model applies to both inference and trainer. GPU counts are split sequentially: inference gets GPU 0, trainer gets GPU 1. vllm_server_host defaults to 0.0.0.0 which can fail as a connect address in some container setups — 127.0.0.1 is safer. micro_batch_size controls how many sequences the trainer processes per gradient accumulation step — 16 OOMs on A6000 48GB even with a 0.6B model because the forward pass materializes the full sequence × vocab logits tensor.

hStart t2f-vllm on GPU 0

Steps h and i must run in the same container. If you are on a cloud provider like RunPod, each SSH connection may land in a different container. Use tmux on the remote: SSH in once, start tmux, split into two panes, and run vLLM in one and the trainer in the other. Or just use t2f-rl which handles this automatically.

shell 
# on the remote, inside tmux
CUDA_VISIBLE_DEVICES=0 t2f-vllm --model <model-id> \
  --enforce-eager --disable-log-requests

Wait for Application startup complete.

Why t2f-vllm not vllm serve? Training needs weight sync. After each step the trainer pushes updated weights from GPU 1 to GPU 0 via NCCL. t2f-vllm adds /init_communicator, /update_weights, /get_world_size endpoints. Regular vllm serve gives 404 on those.

iRun training on GPU 1

In the other tmux pane (same remote session):

shell 
cd /workspace/<project> && source .venv/bin/activate
export HF_TOKEN=your_token
export WANDB_API_KEY=your_key
CUDA_VISIBLE_DEVICES=1 t2f-rl @ configs/t2f-rl/<env-name>.toml

jWhat happens

Step
1 t2f-vllm loads model into GPU 0, starts serving
2 t2f-train loads model into GPU 1, connects to vLLM, initializes NCCL
3 Orchestrator calls env.generate(). Verifiers drives the conversation loop, vLLM generates completions
4 Rollouts scored by rubric, advantages computed, microbatches packaged
5 Trainer forward pass, loss, backprop, optimizer step
6 NCCL weight sync: GPU 1 → GPU 0
7 Back to 3 with updated weights

VLearnings

transformers 5.x breaks vLLM. vLLM 0.10.x calls tokenizer.all_special_tokens_extended, which was removed in transformers 5.x. vLLM crashes on startup with AttributeError: Qwen2Tokenizer has no attribute all_special_tokens_extended. Fix: pin transformers>=4.45,<5 for the vLLM process. But installing t2f-trainer pulls in transformers 5.x again, so the pin gets undone. The cleanest workaround is to downgrade after the t2f-trainer install: uv pip install 'transformers>=4.45,<5'. The trainer itself works fine on 4.x.

verifiers version matters. verifiers==0.1.11 changed resolve_client() and rejects AsyncOpenAI as a client type, which is what the orchestrator passes. The error is ValueError: Unsupported client type: <class 'openai.AsyncOpenAI'>. Fix: pin verifiers==0.1.10. This will likely be resolved in a future verifiers release.

Two SSH sessions can land in different containers. On RunPod (and similar providers), each SSH connection may get its own container instance. vLLM running in one container is unreachable from the trainer in another. Symptoms: Connection error: All connection attempts failed even though vLLM shows Application startup complete. Fix: install tmux on the remote (apt-get update && apt-get install -y tmux) and run both processes from the same session, or use t2f-rl which handles this by launching both in a single remote tmux.

OOM on A6000 48GB with micro_batch_size=16. Even a 0.6B model with LoRA can OOM during the training step if the micro batch is too large. The forward pass on the trainer side materializes the full sequence × vocab logits tensor. Fix: drop micro_batch_size to 4 or 8. Generation batch size (controlled by batch_size and rollouts_per_example) is separate and can stay large.

wandb env var not picked up in remote tmux. Exporting WANDB_API_KEY in one shell does not carry into tmux panes launched by t2f-rl. The trainer prompts interactively for login. Fix: run wandb login before starting training so the key is saved to ~/.netrc.

HF token needs write access. push_to_hub requires a HuggingFace token with write permissions. Read-only tokens fail with 401 Unauthorized on repo creation. Generate a write token at huggingface.co/settings/tokens.

hatchling and editables for --no-build-isolation. When using --no-build-isolation (needed because flash-attn requires torch at build time), the build backend (hatchling) must be in the venv. For editable installs (-e), editables is also needed. Install both before the main install: uv pip install hatchling editables.

vllm_server_host default. The trainer config defaults to vllm_server_host = "0.0.0.0", which is a bind address, not a connect address. In some container setups this fails to connect. Setting vllm_server_host = "127.0.0.1" in the TOML config fixes it.
