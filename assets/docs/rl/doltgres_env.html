Doltgres Environment

Idea for an RL environment backed by Doltgres — a Postgres-compatible, version-controlled database. The model interacts with it through FastMCP tools over stdio. No sandbox, no Docker — just processes.

Architecture

The model never touches Doltgres directly. FastMCP is the boundary.

Model → env_response → FastMCP tools (stdio) → Doltgres (localhost)

FastMCP exposes whatever SQL tools you define — query, insert, create_table, etc. The model can only do what the tools allow. No raw connection string, no escape path.

Doltgres on Env Start

Doltgres is a single Go binary. The environment downloads it on first use and caches it. No node setup, no system deps — anyone who pip installs the environment gets everything.

from pathlib import Path
from urllib.request import urlretrieve

DOLTGRES_PATH = Path("/tmp/doltgres")
DOLTGRES_URL = "https://github.com/dolthub/doltgresql/releases/..."

if not DOLTGRES_PATH.exists():
    urlretrieve(DOLTGRES_URL, str(DOLTGRES_PATH))
    DOLTGRES_PATH.chmod(0o755)

curl works too and is on every Linux box and macOS. The only edge case is a minimal Docker image that stripped it out, but any real GPU node will have it. urllib.request.urlretrieve is the zero-dep alternative — pure stdlib, works everywhere Python works.

FastMCP: Shared vs Per-Rollout

The environment is stateful — each rollout mutates the database. Two ways to handle isolation with FastMCP:

Shared server + branching. One Doltgres instance, one FastMCP server, started at environment init. Each rollout gets its own Dolt branch. setup_state creates the branch, cleanup drops it. The FastMCP server manages a connection pool internally, routing each rollout to its branch.

Environment init:
    Start 1 Doltgres, start 1 FastMCP server

setup_state:
    CREATE BRANCH 'rollout-{id}' on shared Doltgres

env_response:
    Route tool calls to shared FastMCP (with branch context)

cleanup:
    DROP BRANCH 'rollout-{id}'

Fewer processes, Dolt branching handles isolation. The server internals are more complex — connection pool, branch routing per rollout. Single Doltgres process serves all rollouts.

Per-rollout server. Each rollout gets its own Doltgres subprocess + its own FastMCP subprocess. Complete process isolation. Each server is simple — one connection, no routing.

setup_state:
    1. Download doltgres binary (first rollout only, cached)
    2. Create data dir: /tmp/dolt-{rollout_id}/
    3. Start doltgres subprocess on random port
    4. Start FastMCP subprocess over stdio

env_response:
    Pass model messages to FastMCP, return tool results

cleanup:
    Kill both processes, remove data dir

More processes, but each one is trivial. No shared state, no connection pool, no branch coordination. Cleanup is just kill + rm.

Leaning shared. Doltgres branching exists for exactly this — cheap, isolated, concurrent branches on one instance. Per-rollout means N Doltgres processes on a GPU node that's already running vLLM. The shared approach trades server complexity for resource efficiency.
