IMulti-Turn Environments

Every environment is a loop: the model responds, the environment reacts, and state accumulates the full trajectory. Four components drive this.

aPieces

Component Role
dataset row Starting state. Has prompt (initial message) plus extra data in info: follow-ups, ground truths, turn count.
state Mutable dict that accumulates data throughout the rollout. Dataset fields via state["info"] (follow-ups, ground truths, seed), state["answer"]. Runtime fields: trajectory, completion, reward, error. Shared across reward functions: earlier ones can store computed values for later ones to consume.
env_response Your function. Called after each model turn with the full conversation + state. Returns new messages to append. This is where environment logic lives.
@vf.stop Methods that check if the rollout is done. Called after each turn. Return True to end.

Example dataset row:

{
    "prompt": [{"role": "user", "content": "Sort these names: Alice, Bob"}],
    "info": {
        "follow_ups": ["Now add Charlie", "Now add Dan"],
        "ground_truths": [["Alice", "Bob"], ["Alice", "Bob", "Charlie"], ...],
        "num_turns": 3,
    }
}

bLoop

Step
0 setup_state(state) prepares per-rollout resources
1 Model sees accumulated messages, generates response
2 Check @vf.stop: if done, go to 5
3 env_response(messages, state) returns new messages
4 New messages appended to conversation, go to 1
5 Completion rendered into state["completion"], scored by rubric, @vf.cleanup runs

State accumulates the full conversation. Each turn appends to the trajectory. At the end, the whole thing is assembled into state["completion"]:

Turn 1: [{user: "Sort: Alice, Bob"}, {assistant: "Alice, Bob"}, {user: "Now add Charlie"}]
Turn 2: [...all above..., {assistant: "Alice, Bob, Charlie"}, {user: "Now add Dan"}]
Turn 3: [...all above..., {assistant: "Alice, Bob, Charlie, Dan"}] → stop → score

cData Patterns

Pattern How it works
pre-planned Follow-up questions stored in info, pulled out in env_response by turn index
dynamic Responses generated based on what the model did: execute action, return observation
hybrid Dataset has the scaffolding, env_response adapts based on what happens. Most real environments are this. 
# pre-planned: pull from dataset
async def env_response(self, messages, state):
    turn = len([m for m in messages if m["role"] == "assistant"]) - 1
    return [{"role": "user", "content": state["info"]["follow_ups"][turn]}]

# dynamic: react to model output
async def env_response(self, messages, state):
    result = execute_action(messages[-1]["content"])
    return [{"role": "user", "content": result}]

dHierarchy

Everything is a MultiTurnEnv with a different env_response:

Environment (base)
  └── MultiTurnEnv (adds the env_response loop)
        ├── SingleTurnEnv (one turn, no env_response)
        ├── ToolEnv (env_response = execute tool calls, return results)
        │     ├── StatefulToolEnv (persistent state between turns)
        │     │     ├── SandboxEnv (tools run in isolated sandbox)
        │     │     └── BrowserEnv (browser automation)
        │     └── MCPEnv (MCP server tools)
        ├── OpenEnvEnv (talks to OpenEnv server)
        ├── TextArenaEnv (game environments)
        └── CliAgentEnv (terminal/CLI agent in sandbox)

The pattern is always the same: parse the model's last message, execute the action, return the observation as messages. The model never talks to the real system directly. env_response is always the bridge.

eHooks

Verifiers provides a lifecycle. You hook into it, do whatever you want behind the hooks, and return messages.

setup_state(state) → State 
async def setup_state(self, state: vf.State) -> vf.State:
    db = create_world(seed=state["info"]["seed"])
    server = start_mcp_server(db)
    state["db"] = db
    state["server"] = server
    return state

Called once at the start of each rollout. Spin up your external system and store handles in state.

env_response(messages, state) → Messages 
async def env_response(self, messages, state, **kwargs):
    last_msg = messages[-1]
    tool_calls = parse_tool_calls(last_msg)
    results = []
    for call in tool_calls:
        result = await state["server"].call_tool(call.name, call.args)
        results.append({"role": "tool", "content": result, "tool_call_id": call.id})
    return results

Called after every model turn. Receive the conversation so far, do your thing (execute tool calls, query a database, call an API), return the next messages. This is the main integration point. Verifiers doesn't know or care what happens inside.

@vf.stop 
@vf.stop
async def workflow_complete(self, state: vf.State) -> bool:
    return state.get("done", False)

Custom stop conditions. Checked after every turn. Return True to end the rollout. The built-in max_turns_reached is always available.

@vf.cleanup 
@vf.cleanup
async def cleanup(self, state: vf.State) -> None:
    server = state.pop("server", None)
    if server:
        await server.stop()

Called after each rollout completes. Tear down per-rollout resources.

@vf.teardown 
@vf.teardown
async def teardown(self) -> None:
    # clean up anything shared across rollouts
    pass

Called once when the entire environment shuts down. Clean up global resources.

fState

state is the glue. It persists across turns within a rollout and is accessible everywhere – in env_response, stop conditions, cleanup, and rubric scoring functions.

Field Managed by
state["prompt"] verifiers initial prompt messages
state["completion"] verifiers final computed completion
state["trajectory"] verifiers list of {prompt, completion, reward, ...} per turn
state["info"] verifiers per-example data from dataset (ground truths, seeds, config)
state["error"] verifiers any error that occurred
state["db"] you database connection
state["server"] you MCP server handle
state["done"] you custom done flag

gScoring

Rubric functions receive completion and state. Use state to access ground truths, database state, or anything else you stored during the rollout.

Rubric 
async def score(completion, state, **kwargs):
    expected = state["info"]["ground_truths"]
    actual = query_final_state(state["db"])
    return compute_score(actual, expected)

rubric = vf.Rubric(funcs=[score], weights=[1.0])

IIRollout Sequence

Inside env.generate(). Verifiers drives the loop, vLLM generates when asked, the env produces the next message each turn. Scoring happens once at the end: the rubric evaluates all turns together, results flow back to the orchestrator.

Rollout

IIIExecution

Inside env.generate(), rollouts for the same example are grouped and run concurrently. Scoring happens at the group boundary. After that, group structure dissolves.

env.generate() is called with n examples and r rollouts per example. Each example gets r copies, so 10 examples × 3 rollouts = 30 total inputs, grouped into 10 groups of 3.

aConcurrency

Level Parallel? Mechanism
groups yes asyncio.create_task per group, semaphore-bounded
rollouts in group yes All rollouts for same example run concurrently
turns in rollout no Sequential: model, env_response, model, ...
scoring per group All rollouts finish, then rubric scores the group

A group is the atomic unit. All its rollouts must finish before anything gets scored or reported. asyncio.as_completed picks up finished groups in whatever order they complete, fires on_progress, and saves results incrementally. You don't wait for all groups to finish.

t=0  Launch Group0(A), Group1(B), Group2(C)      ← all as async tasks
t=1  Group0: rollout0 turn1, rollout1 turn1       ← parallel within group
     Group1: rollout0 turn1, rollout1 turn1
     Group2: rollout0 turn1, rollout1 turn1
t=2  Group1 finishes first → rubric → on_progress → save
t=3  Group0 finishes       → rubric → on_progress → save
t=4  Group2 finishes       → rubric → on_progress → save
t=5  All done, return results

bHandoff

Once groups are scored, the group structure is no longer needed. The orchestrator collects scored rollouts, computes advantages (this still needs the group, since advantage = reward minus group mean), then packages everything into microbatches. Microbatches don't respect group boundaries: they're just chunks of rollouts sized for GPU memory. From there, the trainer processes one microbatch at a time.
