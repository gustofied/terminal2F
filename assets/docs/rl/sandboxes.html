Sandboxes

RL agents act on environments. Those environments need isolation — each rollout must run in its own stateful sandbox so parallel rollouts don’t corrupt each other. The model never touches the sandbox directly. It talks through FastMCP tools over stdio. The sandbox sits behind them.

Model → FastMCP (stdio) → Sandbox (isolated runtime)

Three Questions

When evaluating any sandbox, ask three things (Livshits):

  1. Boundary — what is shared between this code and the host?
  2. Policy — what can the code touch? (files, network, devices, syscalls)
  3. Lifecycle — what survives between runs?

If you can answer those, you understand your sandbox. If you can’t, you’re guessing.

Boundary

Moving left to right, direct syscall exposure to the host kernel shrinks:

BoundaryWhat happens
ContainerProcesses in separate namespaces, still one host kernel. Syscalls go straight to the host.
gVisorUserspace kernel (Sentry) intercepts syscalls. Only ~68 host syscalls exposed.
MicroVMGuest kernel behind hardware virtualization. Host sees KVM ioctls, not the workload’s syscalls.
WASM / IsolateNo syscall ABI at all. Guest only gets capabilities the host explicitly provides.

Stronger boundary doesn’t mean simpler — it means you’re betting on different code. Containers bet on the host kernel. gVisor bets on its Sentry. MicroVMs bet on KVM + VMM. WASM bets on the runtime.

Policy

A tight policy in a weak boundary is still a weak sandbox. A strong boundary with a permissive policy is a missed opportunity. Policy covers: filesystem paths, network destinations, process creation, device access, resource quotas, and the interface surface itself.

For our RL envs, FastMCP tools are the policy. The model can only call draw_line, query, screenshot — whatever tools the server exposes. No shell, no arbitrary syscalls, no filesystem access. The tools have typed inputs. This is capability-scoped by design, which is why we can use lighter boundaries than agents that run arbitrary code.

For our envs: drawing is fresh (Canvas starts blank, instant anyway). Doltgres is snapshot/restore at the data level — seed the database once, branch per rollout, drop the branch on cleanup. Dolt branching is snapshot/restore without VM-level machinery.

The Three Approaches

Everyone who ships agent sandboxes lands on the same three solutions (Livshits).

1. Simulated Environments

No real OS at all. Everything happens in JavaScript or WASM. Instant startup, no kernel, no container.

  • WebContainers — Node.js compiled to WASM. Millisecond startup. Anything that runs on Node runs here: HTML Canvas, PGLite, Express, file I/O. JS/Node only — no native binaries, no C extensions.
  • just-bash (Vercel) — TypeScript implementation of bash with in-memory filesystem. 40+ Unix utilities. <1ms startup. Can wire in custom CLIs and DuckDB.
  • AgentVM — full Alpine Linux VM compiled to WASM via container2wasm. Experimental.
  • Monty (Pydantic) — minimal Python interpreter in Rust. Born from the failure of mcp-run-python: pyodide isn’t safe — Python in WASM can run arbitrary JS, taint the runtime, and OOM the machine. Monty is purpose-built with security as a constraint.

Note: WebContainers specifically is browser-only (it needs Service Workers, SharedArrayBuffer). It works for in-browser dev tools (StackBlitz, CodeSandbox) but not on headless GPU servers. For headless WASM sandboxes, look at Wasmer, Wasmtime, or WasmEdge — but those don’t have Canvas. PGLite (Postgres compiled to WASM) is the strongest RL use case for WASM today — it runs headlessly via any WASM runtime.

Note on safety: the pyodide problem matters if you give agents a run_code tool. Our envs use predefined tools with typed inputs — the model can’t inject arbitrary code.

2. OS-Level Isolation (Containers)

Real code against a real kernel, but restricted. The workhorse.

  • Docker / Podman — the default. Seconds to start. For RL, a 2-second startup across 10,000 rollouts is 5+ hours of spawning overhead.
  • gVisor — userspace kernel that intercepts syscalls. Drops host exposure to ~68 syscalls. What Archipelago uses for code execution. What Claude uses on the web (runsc hostname). Fits into Docker/Kubernetes as an OCI runtime. Trade-off: not every syscall is identical — there’s a compatibility matrix.
  • OS primitives — no containers at all. Claude Code uses bubblewrap (Linux) and Seatbelt (macOS). OpenAI’s Codex CLI uses Landlock + seccomp (Linux), Seatbelt (macOS). Just OS-level restrictions on a process.

Containers share the host kernel. A kernel bug in any allowed syscall path is a host bug. Hardening (seccomp, AppArmor, user namespaces) tightens policy but doesn’t change the boundary.

3. MicroVMs

True VM-level isolation. Each agent gets its own kernel, its own memory space, hardware-enforced boundaries.

  • Firecracker — AWS’s VMM for Lambda/Fargate. ~125ms boot, ~5MB overhead. One process per microVM, minimal virtio devices, jailer for host confinement. 24 whitelisted syscalls. Supports snapshot/restore.
  • E2B — Firecracker/Cloud Hypervisor underneath. <200ms cold start. 200M+ sandboxes served. Managed, costs money.
  • Fly Sprites — persistent Linux VMs that sleep when idle. Create in 1–2s, checkpoint in ~300ms, restore instantly. Durable storage. “You’re not helping the agent by giving it a container. They don’t want containers.”
  • Daytona — stateful sandboxes: start, pause, fork, snapshot, resume. Sub-90ms cold start. Best framing of the RL sandbox problem.
  • Modal — Python-native, runtime-defined containers on demand. Up to 24h. Good for batch/RL workloads.
  • Cloudflare — containers on edge infra. Good if you’re already in the ecosystem.
  • Prime Intellect — their own sandbox infra. Relevant since we use verifiers.

MicroVMs shift the attack surface from host kernel syscalls to KVM ioctls + VMM device I/O. Stronger isolation, but you now have two kernels to patch.

The rule of thumb from Livshits: “If you can model the task as capability-scoped operations: prefer Wasm/isolate.” That’s exactly what FastMCP tools are — predefined operations with typed inputs. We start at the lightest boundary and escalate only if the environment demands it.

No containers, no VMs. The model talks through FastMCP tools — that’s the policy. Each env picks the lightest boundary that works:

  • Drawing — needs real Canvas, so Playwright provides a headless browser. The FastMCP App (ui:// resource) serves the same Canvas HTML for both training (Playwright renders it headlessly, returns screenshots) and visualization (human opens it in a browser, watches live).
  • PGLite — Postgres compiled to WASM. Runs headlessly via any WASM runtime (Wasmer, Wasmtime). No binary to download, no process to manage. This is where WASM shines for RL — instant startup, strong isolation, real SQL.
  • Doltgres — real Go binary as a subprocess. No sandbox needed — FastMCP tools are the boundary. Branching handles per-rollout isolation at the data level.
  • Email-to-CC-BCC — pure Python, in-process. No sandbox at all.

At Scale: Remote Sandboxes

When sandbox startup and density matter, move them off the GPU node:

GPU cluster (inference) ←→ API ←→ CPU cluster (sandboxes)

Inference nodes run the model. Sandbox nodes run environments. They scale independently. GPUs stay busy, environments scale horizontally. The FastMCP interface stays the same — stdio locally becomes HTTP remotely. Same tools, same protocol, different transport.

For now: build local, everything on one machine. The MCP abstraction buys the flexibility to split later without rewriting the environment.
