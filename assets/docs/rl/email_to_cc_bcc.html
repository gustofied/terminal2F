1. Email-to-CC-BCC

Email-to-CC-BCC is an environment built to evaluate and train models on recipient placement via RLVR (GRPO), using the verifiers framework and t2f-trainer (a slightly adjusted verifiers-rl). The thinking is that the task is a good fit for RL because it has a clear verifiable reward signal (set match against ground truth), structured output (JSON), and enough ambiguity in the CC/BCC split that a model has to reason about roles, sensitivity, and hierarchy rather than pattern match. A synthetic dataset is generated using NVIDIA NeMo DataDesigner, then used to train Qwen models and compare against OpenAI baselines to gauge what stronger models can do out of the box. The environment supports 1, 2, and 3 turn rollouts as a form of curriculum, not increasing difficulty but expanding the number of recipient reassignment decisions the model must handle. Some terminology used throughout comes from verifiers.

ITask

Given 7 people and an email thread, assign each person to To, CC, or BCC. The thread evolves across turns and recipients shift.

Each row has 7 people with name, email address, and role. The model sees the full roster and an email, then outputs a JSON object placing each relevant person into the correct field. On follow-up turns, a new email arrives in the thread and the model re-evaluates.

load_environment assembles the first prompt from the dataset's email_list and question_1 columns:

turn 1 
An email thread is unfolding. For each email, decide who
belongs in To, CC, and BCC. Recipients may change as the
thread evolves.

Possible recipients:
- Sarah Chen <sarah.chen@acme.com> - Project Lead
- Mike Torres <mike.t@clientcorp.com> - Client PM
- Lisa Park <lisa.park@acme.com> - VP Engineering
  ...

Subject: Q3 deadline extension request

Hi team, I wanted to flag that we're going to need
a 2-week extension on the Phoenix deliverables...

Provide your answer as JSON: {"to": [...], "cc": [...], "bcc": [...]}
Use email addresses, not names.

Follow-up turns feed the next email from info["follow_ups"] via env_response:

turn 2+ 
New email in the thread. Re-evaluate recipients.

Subject: Re: Q3 deadline extension request

Lisa, thanks for looping me in. I've reviewed the timeline
with the client and can confirm...

Provide your answer as JSON.

Expected output on each turn:

json 
{
  "to": ["sarah.chen@acme.com"],
  "cc": ["mike.t@clientcorp.com"],
  "bcc": ["lisa.park@acme.com"]
}

max_turns controls how many turns the environment runs (1, 2, or 3). The stop condition checks len(trajectory) >= num_turns. Scoring uses Jaccard index per field per turn, averaged across all turns in the rollout.

IIDataset

In verifiers, the dataset is the initial prompt of an environment. Each row becomes one rollout, one full trajectory. The framework uses HuggingFace datasets natively, so hosting on HuggingFace and loading via load_dataset is the natural path. That is why this dataset is hosted there.

The dataset is a flat parquet with 7 columns. One row is one complete 3-turn scenario:

Column Description
email_list The 7 people, always present. Each entry is name <email> - role.
question_1 Initial email (subject + body). The environment prepends email_list and appends the instruction at runtime.
question_2, 3 Follow-up replies as the situation evolves (people added, removed, escalation, etc.).
answer_1, 2, 3 Ground truth JSON: {"to": [...], "cc": [...], "bcc": [...]}

load_environment reshapes the flat columns into the verifiers format:

python 
"prompt": [{"role": "user", "content": email_list + question_1 + instruction}],
"info": {
    "follow_ups": [question_2, question_3],
    "ground_truths": [answer_1, answer_2, answer_3],
    "num_turns": max_turns,
}

aData Generation

A dataset was needed to train on, so DataDesigner was the tool of choice. Below is the thinking behind how the v1 dataset was built. Some of these choices get revisited in later sections as the dataset evolves.

  1. Sample people - 7 per row with name, email, role. 2-6 start active, rest are reserve. One company domain per row, one external domain. Roles sampled without replacement.
  2. Assign recipients per turn - deterministic. Sensitivity drives BCC, hierarchy drives To vs CC. Changes between turns (escalation, person added, made confidential, etc.) retry if they'd be a no-op.
  3. LLM writes email content - given the roster and visible recipients (To/CC only, no BCC), generate realistic email thread. The LLM never sees BCC assignments.

IIIRewards

Verifiers scores the full rollout once at the end. The rubric receives the complete state object, which includes all turns and all ground truths. Each reward function can loop through individual turns, score each one against its ground truth, and average them into a single number. GRPO only sees that final scalar for the entire trajectory, there is no per-turn reward signal to the trainer. But because the state object gives access to all turns, the reward function can bake per-turn correctness into that scalar (e.g. a model that gets turn 1 right but fails turn 3 still gets partial credit). The rubric then combines all functions via weighted sum into one reward for the trainer.

Function What
to_correct Jaccard on To field
cc_correct Jaccard on CC field
bcc_correct Jaccard on BCC field

Each function averages its score across all expected turns (missing turns count as 0, so a model that stops early is penalized). Weighted equally (1/3 each) by the rubric. Jaccard index: |intersection| / |union|, 1.0 if both sets empty. Exception: BCC scores 0.5 when both predicted and expected are empty, so rows without BCC recipients are not a free point. This is a hacky fix for a data problem (too many rows with empty BCC), and it could backfire if the model learns to always stuff someone into BCC to avoid the penalty.

Knobs (--env-args): max_turns (1, 2, or 3). Slices dataset accordingly.

IVResults v1

aTo vs CC is Noisy

distribute_emails() shuffles active people before assigning To and CC. The model has some signal from the email text (who is addressed, who is asked to act, hierarchy cues), but the ground truth split comes from a random shuffle. The model cannot fully recover it. BCC is also noisy: sensitivity controls whether people go to BCC, but who goes there is still drawn from shuffled active participants. Active people who are greeted in the email can end up in BCC, which is why 75% of BCC recipients appear in the text.

This means all three individual scores (to_correct, cc_correct, bcc_correct) have noise. With the rubric at equal 1/3 weights, two-thirds of the reward signal that GRPO uses to rank rollouts is driven by noise the model cannot learn from, leaving BCC as the only clean signal at 1/3 weight. The visible set (To + CC combined) is the most learnable signal. One upgrade would be to replace the rubric with visible_correct (Jaccard on To ∪ CC) + bcc_correct + format_correct (valid JSON with correct keys), dropping individual To/CC scoring entirely.

The real fix is to replace the shuffle with rules driven by scenario type, hierarchy, audience, and roles. The person being asked to act goes to To (picked by scenario-to-role priority), managers and stakeholders go to CC (shaped by hierarchy), compliance observers from reserve go to BCC (when sensitivity is high). Active participants never end up in BCC. This makes the exact To/CC/BCC split derivable from the observation without turning it into greeting-parsing.

bFix the Rubric, Not the Data

Scoring To and CC separately with GRPO hence becomes a problem. Rollouts get ranked against each other on a distinction that is partly random, and GRPO amplifies that noise into policy updates. The fix for v1 without regenerating data: replace the three-way rubric with visible_correct (set match on To ∪ CC) + bcc_correct (set match on BCC) + format_correct (valid JSON). Drop individual To/CC rewards entirely. Re-add them in v2 once distribute_emails() is deterministic.

That said, this is a second-order fix. Collapsing To and CC into a single visible set just to get a reward curve going up is reward shaping for something the model is not actually learning to distinguish. The reward goes up, but the underlying capability (correct To vs CC placement) is not being trained. It is useful to get a first run going, but it should not be mistaken for the real thing.

cKnown Data Issues

Looking at the v1 parquet (5,000 rows):

  • BCC recipients mentioned in email text (75%). The generating LLM was given only visible recipients (To/CC) as a hint, but it mentions BCC people by full name 75% of the time anyway (non-BCC: 64.5%). It largely ignores the hint and references everyone on the roster. 1.9% of rows have BCC people directly addressed or greeted. This is the biggest issue: the model being trained could learn to infer BCC from who is named but absent from To/CC, or just get confused by the contradiction.
  • Q2 near-duplicates of Q1 (~2%). 0.8% verbatim, 2.3% sharing the first 100 characters. Answers still differ across turns, but the thread does not evolve for these rows.
  • No field overlap. To/BCC and CC/BCC overlap is 0% across all turns. No person appears in multiple fields.

The BCC mention rate is the real problem. None of these block a first training run, but the generation prompts need tightening for v2. A check script lives at nuggets/email-to-cc-bcc/check_data.py.

dmbox Format

mbox is a standard mail format. The current dataset uses a custom plain-text layout for emails, but mbox gives real structure: proper headers, threading, multipart bodies. Using mbox instead could make the task more realistic and potentially more trainable, since the model would work with the same format actual mail clients and servers use. Python stdlib has mailbox.mbox built in. Worth exploring for a future version.
