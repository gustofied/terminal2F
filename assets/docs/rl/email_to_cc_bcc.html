1. Email-to-CC-BCC

Email-to-CC-BCC is an environment built to evaluate and train models on recipient placement via RLVR (GRPO), using the verifiers framework and t2f-trainer (a slightly adjusted verifiers-rl). The thinking is that the task is a good fit for RL because it has a clear verifiable reward signal (set match against ground truth), structured output (JSON), and enough ambiguity in the CC/BCC split that a model has to reason about roles, sensitivity, and hierarchy rather than pattern match. A synthetic dataset is generated using NVIDIA NeMo DataDesigner, then used to train Qwen models and compare against OpenAI baselines to gauge what stronger models can do out of the box. The environment supports 1, 2, and 3 turn rollouts as a form of curriculum, not increasing difficulty but expanding the number of recipient reassignment decisions the model must handle. Some terminology used throughout comes from verifiers.

ITask

Given 7 people and an email thread, assign each person to To, CC, or BCC. The thread evolves across turns and recipients shift.

Each row has 7 people with name, email address, and role. The model sees the full roster and an email, then outputs a JSON object placing each relevant person into the correct field. On follow-up turns, a new email arrives in the thread and the model re-evaluates.

load_environment assembles the first prompt from the dataset's email_list and question_1 columns:

turn 1 
You are given an email thread. For each email, assign
the correct To, CC, and BCC recipients. Recipients may
change between emails as the situation evolves.

Roster:
- Sarah Chen <sarah.chen@acme.com> - Project Lead
- Mike Torres <mike.t@clientcorp.com> - Client PM
- Lisa Park <lisa.park@acme.com> - VP Engineering
  ...

Subject: Q3 deadline extension request

Hi team, I wanted to flag that we're going to need
a 2-week extension on the Phoenix deliverables...

Reply with JSON only: {"to": [...], "cc": [...], "bcc": [...]}
Use email addresses, not names.

Follow-up turns feed the next email from info["follow_ups"] via env_response:

turn 2+ 
Next email in the thread:

Subject: Re: Q3 deadline extension request

Lisa, thanks for looping me in. I've reviewed the timeline
with the client and can confirm...

Reply with JSON only.

Expected output on each turn:

json 
{
  "to": ["sarah.chen@acme.com"],
  "cc": ["mike.t@clientcorp.com"],
  "bcc": ["lisa.park@acme.com"]
}

max_turns controls how many turns the environment runs (1, 2, or 3). The stop condition checks len(trajectory) >= num_turns. Scoring uses Jaccard index per field per turn, averaged across all turns in the rollout.

IIDataset

In verifiers, the dataset is the initial prompt of an environment. Each row becomes one rollout, one full trajectory. The framework uses HuggingFace datasets natively, so hosting on HuggingFace and loading via load_dataset is the natural path. That is why this dataset is hosted there.

The dataset is a flat parquet with 7 columns. One row is one complete 3-turn scenario:

Column Description
email_list The 7 people, always present. Each entry is name <email> - role.
question_1 Initial email (subject + body). The environment prepends email_list and appends the instruction at runtime.
question_2, 3 Follow-up replies as the situation evolves (people added, removed, escalation, etc.).
answer_1, 2, 3 Ground truth JSON: {"to": [...], "cc": [...], "bcc": [...]}

load_environment reshapes the flat columns into the verifiers format:

python 
"prompt": [{"role": "user", "content": email_list + question_1 + instruction}],
"info": {
    "follow_ups": [question_2, question_3],
    "ground_truths": [answer_1, answer_2, answer_3],
    "num_turns": max_turns,
}

aData Generation

A dataset was needed to train on, so DataDesigner was the tool of choice. Below is the thinking behind how the v1 dataset was built. Some of these choices get revisited in later sections as the dataset evolves.

  1. Sample people - 7 per row with name, email, role. 2-6 start active, rest are reserve. One company domain per row, one external domain. Roles sampled without replacement.
  2. Assign recipients per turn - deterministic. Sensitivity drives BCC, hierarchy drives To vs CC. Changes between turns (escalation, person added, made confidential, etc.) retry if they'd be a no-op.
  3. LLM writes email content - given the roster and visible recipients (To/CC only, no BCC), generate realistic email thread. The LLM never sees BCC assignments. v1 used google/gemini-2.5-flash via OpenRouter.

IIIRewards

Verifiers scores the full rollout once at the end. The rubric receives the complete state object, which includes all turns and all ground truths. Each reward function can loop through individual turns, score each one against its ground truth, and average them into a single number. GRPO only sees that final scalar for the entire trajectory, there is no per-turn reward signal to the trainer. But because the state object gives access to all turns, the reward function can bake per-turn correctness into that scalar (e.g. a model that gets turn 1 right but fails turn 3 still gets partial credit). The rubric then combines all functions via weighted sum into one reward for the trainer.

Function What
to_correct Jaccard on To field
cc_correct Jaccard on CC field
bcc_correct Jaccard on BCC field

Each function averages its score across all expected turns (missing turns count as 0, so a model that stops early is penalized). Jaccard index: |intersection| / |union|, 1.0 if both sets empty. Exception: when GT BCC is empty, empty predictions score 0.2 (small credit) and non-empty predictions score 0.0 (penalizes hallucination), so turns without BCC recipients are not a free point but still lightly regularize against spurious output. Weights are To 0.45, CC 0.45, BCC 0.10. BCC is downweighted because ground truth BCC is empty on ~60% of turns, which inflates the metric without any model skill. This is not to make BCC learn fast; it is to prevent reward inflation from empty/empty while still discouraging spammy BCC.

Training on this data would push Qwen toward 0.43 by learning the same surface heuristics frontier models use, but 0.43 is the ceiling with this dataset.

Looking at individual rollouts, the models are often more correct than the ground truth. Claude Sonnet 4.6 on a complaint email: correctly places the addressee in To, all mentioned stakeholders in CC, empty BCC. Reasoning is sound ("this is a formal complaint where transparency among all parties is important"). The ground truth disagrees on one CC entry because the shuffle happened to assign it differently. DeepSeek R1 on a vendor update: excludes a person from CC because "her support has already been secured," a reasonable reading of the email. The ground truth includes her anyway. In both cases the model is doing better email reasoning than the labels. Training with RL on these labels would push models away from good judgment and toward matching random assignments.

bWhy the Ceiling is Low

distribute_emails() shuffles active people before assigning To and CC. The ground truth split comes from a random shuffle, not from the email content. The model has some signal (who is addressed, who is asked to act), but it cannot fully recover a random permutation. BCC is also noisy: sensitivity controls whether people go to BCC, but who goes there is still drawn from shuffled active participants. Active people who are greeted in the email can end up in BCC, which is why 75% of BCC recipients appear in the text.

With the rubric at equal 1/3 weights, two-thirds of the reward signal that GRPO uses to rank rollouts is driven by noise the model cannot learn from, leaving BCC as the only clean signal at 1/3 weight.

cRubric Fix (Second-Order)

One option without regenerating data: replace the three-way rubric with visible_correct (Jaccard on To ∪ CC) + bcc_correct + format_correct (valid JSON). Drop individual To/CC scoring. This would get a reward curve going up, but collapsing To and CC into a single visible set is reward shaping for something the model is not actually learning to distinguish. The reward goes up, but the underlying capability is not being trained. Useful to get a first run going, but it should not be mistaken for the real thing. If the goal were just to get learning signal without regenerating data, this is the quickest path, but it is not the option to go for.

dData Fix (The Real One)

Replace the shuffle with deterministic rules. The person being asked to act goes to To (picked by scenario-to-role priority), managers and stakeholders go to CC (shaped by hierarchy), compliance observers from reserve go to BCC (when sensitivity is high). Active participants never end up in BCC. This makes the exact To/CC/BCC split derivable from the observation. The LLM generation prompts also need tightening: BCC people should not appear in the email text at all.

eKnown Data Issues

Looking at the v1 parquet (5,000 rows):

  • BCC recipients mentioned in email text (75%). The generating LLM was given only visible recipients (To/CC) as a hint, but it mentions BCC people by full name 75% of the time anyway (non-BCC: 64.5%). 1.9% of rows have BCC people directly addressed or greeted.
  • Q2 near-duplicates of Q1 (~2%). 0.8% verbatim, 2.3% sharing the first 100 characters. Answers still differ across turns, but the thread does not evolve for these rows.
  • No field overlap. To/BCC and CC/BCC overlap is 0% across all turns.

A check script lives at nuggets/email-to-cc-bcc/check_data.py.

fEmail Format

v1 uses a bare plain-text layout (Subject + body). v2 should add Date: and From: headers to make the emails look like actual emails, without including To:/CC:/BCC: (since that is what the model has to figure out).

Vv2

aChanges

v2 rewrites the data generation pipeline to fix the noise problems identified in v1. The core changes:

  • Sender exclusion. The sender is picked first and removed from all recipient fields. If removing the sender empties To, the first CC person gets promoted.
  • Deterministic routing. To/CC/BCC assignment is based on role priority, not random shuffle. Two separate maps: ACTION_PRIORITY (lower number = more likely action owner, used for To selection) and SENIORITY (higher number = more senior, used for sender selection and "upward" promotion). Using one scale for both was brittle because action ownership and organizational rank do not align.
  • BCC from reserve only. Active participants never go to BCC. Compliance mode pulls Legal/HR/Finance from the reserve pool. Broadcast mode moves all external contacts to BCC for privacy, keeping To and CC internal-only.
  • Mode/audience coupling. Broadcast mode requires an external audience (with_client, with_vendor, etc.). If the sampled audience is internal-only, mode flips to normal. Without this, broadcast becomes random text decoration with empty BCC and the model cannot learn anything from it.
  • Primary action owner in prompt. The LLM prompt includes a "primary action owner" field pointing to the To person. The email must explicitly task or address that person. This closes the learnability gap where v1 labels were deterministic but the email text did not consistently imply the To choice.
  • Mentionable-names-only. The LLM prompt only lists To+CC recipients. BCC names are hidden from the generation prompt entirely, so the model cannot leak them into the email text.
  • Monotonic timestamps. Each reply is dated after the previous one.

bValidation

A post-generation validator rejects rows where: the sender appears in any answer field, BCC names (full or first name) appear in the email text, non-mentionable roster names appear in the text, any field overlap exists, To is empty, or a broadcast/compliance cue is present but BCC is empty.

When generating synthetic data with LLMs, it is usually cheaper and more reliable to over-generate and then filter with a strict validator than to try to prompt away every failure mode. LLMs will occasionally ignore constraints, drift, or hallucinate details. If you can encode the invariants you actually care about (schema, allowed entities, cue presence, no contradictions) as fast deterministic checks, generate more, validate hard, and keep only what passes. Monitor rejection rates to avoid skewing the distribution.

cNew dataset

  • Target ~5000 validated rows after filtering (generated 7500, validator rejects noise).
  • 3-turn multi-turn conversations with monotonic dates.
  • Mbox-style email format with Date: and From: headers, replacing v1's bare plain-text layout.
  • Sender excluded from all answer fields. No BCC name leakage in email text.
  • To recipient is always explicitly tasked or addressed in the email body.
  • BCC is only compliance (Legal/HR/Finance from reserve) or broadcast (all externals). Never random.
  • Rubric reweighted to To 0.45, CC 0.45, BCC 0.10. BCC on empty-GT turns: 0.2 for correct empty, 0.0 for spurious non-empty. Non-empty GT uses standard Jaccard.

dActual new dataset

Generated 7500 rows and ran validate_row() to filter. 4991 passed (33.5% rejection rate). The validator checks per turn: To not empty, no field overlap, BCC names not in email text, sender not in any answer field, only mentionable names in text, and broadcast/compliance cue implies non-empty BCC. 

def validate_row(row):
    for turn in [1, 2, 3]:
        answer = json.loads(row[f"answer_{turn}"])
        question = row[f"question_{turn}"]
        to_set, cc_set, bcc_set = set(answer["to"]), set(answer["cc"]), set(answer["bcc"])

        if not answer["to"]:                           # empty To
            return False
        if to_set & cc_set or to_set & bcc_set or cc_set & bcc_set:  # field overlap
            return False
        for bcc_email in answer["bcc"]:                # BCC name leakage
            name = email_to_name.get(bcc_email, "")
            if name.lower() in question.lower():
                return False
            first = name.split()[0]
            if len(first) > 2 and first.lower() in question.lower():
                return False
        if sender_email in to_set | cc_set | bcc_set:  # sender in fields
            return False
        if (has_broadcast_cue or has_compliance_cue) and not bcc_set:  # cue without BCC
            return False
    return True

eTakeaways

Split architecture. Deterministic code handles ground truth routing, the LLM handles natural language content. Trying to make the LLM do both (v1 with random shuffle for routing) is where noise enters. Keep the verifiable part in code.

Independent sampling of correlated dimensions breaks things. Mode and audience were sampled independently, which created broadcast mode with no externals. Any time two sampled variables have a logical dependency, either couple the sampling or fix it downstream.

Deterministic labels are necessary but not sufficient. v1's problem was random routing. But even after fixing that, the text still did not imply the To choice. The model needs the email to actually task the To person, otherwise the mapping from text to label is not learnable. Injecting "primary action owner" into the generation prompt closes that gap.

One priority scale for two concepts fails. Action ownership (who does the work) and seniority (who has authority) are different axes. Junior engineers do the work, VPs send the emails. Conflating them into one number creates contradictions. Split into ACTION_PRIORITY and SENIORITY.

Ceiling test before training. Running frontier models (GPT-5, Claude 4.6) on v1 and seeing them all hit the same ~0.44 wall confirmed the problem was data, not model capability. Saved GPU hours that would have been wasted on bad data.

BCC is a hidden-information problem. The model must infer BCC from contextual cues (confidentiality phrases, broadcast language) rather than from who is mentioned. That makes it fundamentally harder than To/CC and explains why BCC scores were consistently lowest across all baselines.

fEvaluation stage

First v2 evals (GPT-4.1-mini, GPT-5, equal 1/3 weights) showed reward ~0.59, up from ~0.44 on v1. But bcc_correct at ~0.8 was misleading: ground truth BCC is empty on ~60% of turns, and models predict empty BCC 97% of the time. They scored high by doing nothing. Fixed by reweighting to To 0.45, CC 0.45, BCC 0.10 and scoring BCC empty/empty as 0.0.

A small regularizer handles the empty BCC case: empty/empty scores 0.2 (tiny credit for correctly leaving BCC empty), non-empty when GT is empty scores 0.0 (penalizes hallucination). Non-empty GT turns use standard Jaccard. With BCC weighted at 0.10, the regularizer contributes at most 0.02 to the total reward per turn. This is a reasonable tradeoff: it prevents empty/empty from inflating the reward while still giving a small signal against spammy BCC predictions.

The n=50 run on GPT-4.1-mini (v0.1.7) gives a clearer picture. 150 rollouts, 450 turns total.

The number one problem is To/CC confusion. 40% of all turns have a CC recipient placed in To instead. The model knows who should be on the email, it just does not distinguish between "must act" and "kept in the loop." The sender-as-recipient error is interesting too: the model includes the email sender (usually in CC) 16% of the time, which is always wrong in the ground truth.

On BCC: 60% of turns have empty GT, 40% have non-empty. When GT is empty the model correctly predicts empty 97% of the time. When GT is non-empty the model misses it 96% of the time (mean score 0.026). It essentially never predicts BCC. Even perfect To and CC cannot reach 1.0 unless the model also hits BCC on the turns where GT BCC is non-empty.

Errors are also deterministic. 11 of 50 examples have near-zero variance across 3 rollouts. The model gives the same answer every time. The hardest example scores 0.118 and fails identically all 3 rollouts. This is good news for training: the mistakes are systematic, not random, so GRPO has patterns to push against.

The real question is whether this environment is trainable at all. Frontier models top out around 0.45 reward, and the gap between them and smaller models is narrow. The remaining errors are not from lack of capability but from ambiguity: "reply-to bias" (models put the person being replied to in To instead of the action owner) and "all-in-To" (dumping everyone into To, leaving CC empty), both of which are valid email styles that just disagree with the dataset's policy. The next step is to eval a very small model (Qwen 3B or 0.5B). If it scores around 0.10, there is headroom to train it up toward 0.4 with GRPO. If even small models score 0.3+, the task is too easy or too ambiguous for RL to add value, and the environment needs more work before training makes sense.

BCC carries no signal in practice: all models score ~0.13 no matter the size, just the regularizer on empty-GT turns. The v2 dataset does make BCC inferable (compliance roles from reserve, broadcast mode for externals), but models still default to "BCC is rare, leave it empty." They are following general email etiquette rather than reading the cues in the scenario. Any training signal has to come from To and CC.

Building environments like this one is harder than it looks. The task is not just "pick the right recipients." There is reasoning behind where to put people, and that reasoning is not well-defined. There is email etiquette, sure, but there is no universal rule for what goes in To vs CC. It depends on the company, its culture, whether "To" means "action owner" or just "the person you are replying to." Different organizations do it differently. So the environment is trying to teach a policy that does not really exist as a single ground truth, which is why even frontier models disagree with the labels in reasonable ways.

This environment has been a solid learning exercise for building RLVR pipelines: data generation, scoring, rubric design, eval tooling. But for actual training it probably needs either a prompt contract or a data regen that makes the action-owner distinction unambiguous in the email text. Without that, the reward signal is too noisy for the model to learn the right thing. It might be too ambiguous as it stands, and maybe the move is to come back to this environment later with a clearer policy baked into the data. But first, let's see what a smaller model (Qwen 3B or 0.5B) can do. If there is real headroom, it is still worth a training run.

Turn 1 is perfect. By turn 3 almost 40% of responses fail to produce valid JSON, mostly the model getting stuck in its thinking block and never outputting an answer. Worth a run.

One thing worth checking: is the problem reasoning or just model size? Qwen3-0.6B is a thinking model, it wraps every answer in <think> blocks. All 450 turns use them. The model reasons through the scenario, often correctly identifying roles and relationships, then still outputs the wrong recipients. But our parser does not care about the thinking tokens. It finds the last JSON object in the response, so <think>...</think> followed by JSON parses fine. A non-reasoning model of the same size might actually do better here, since it would not burn its token budget on chain-of-thought that leads nowhere. Could be worth a side-by-side: same parameter count, reasoning on vs off.

gNext up

So let's do a  few targeted evals to figure out what is actually going wrong. The turn-3 JSON collapse (62% valid) is the biggest open question: is it a reasoning problem or a format problem? And separately, does the 3-turn setup hurt more than it helps at this model size?

1. Reasoning vs non-reasoning. Run the same eval set with two variants of the same model size:

  • Qwen3-0.6B thinking (already ran, baseline)
  • Qwen3-0.6B with thinking disabled, or Qwen2.5-0.5B-Instruct

Track two things: JSON validity per turn, and conditional To/CC scores (only on turns where JSON is valid). If the non-reasoning model has much higher JSON validity but similar To/CC scores, the problem is format stability, not capability. The thinking tokens are wasting the context window and causing the model to lose track of the output format. If non-reasoning fixes JSON but To/CC gets worse, then reasoning does help with placement, it just cannot maintain format. Either way, separating "can it produce valid JSON" from "can it place recipients correctly" tells you what training needs to fix first.

2. Fewer turns. Run max_turns=1 on the 0.6B model. Turn 1 already has 100% JSON validity, so this isolates recipient placement quality without the format collapse. If reward jumps significantly (say from 0.108 to 0.2+), the 3-turn setup is dragging the score down more than the actual placement errors. Could be worth starting training on single-turn first as a curriculum, then scaling to 3 turns once the model has learned basic format and placement.

3. What to look for.

  • Does disabling thinking fix JSON validity on later turns?
  • Does single-turn eval show meaningfully higher reward?
  • Is the To/CC confusion consistent across setups, or does it shift with turns and reasoning mode?

The answers shape the training strategy. If format is the bottleneck, training on single-turn first makes sense, the model learns "always output JSON" before tackling multi-turn. If placement is the bottleneck, jump straight to 3-turn training and let GRPO handle format as a side effect.

One idea if format turns out to be the bottleneck: do GRPO on single-turn first, get the model to reliably output valid JSON with decent placement. Then collect good multi-turn trajectories from that model and SFT on them. So RL teaches format and basic placement on turn 1, then SFT on multi-turn data teaches the model to maintain that across all three turns. Otherwise 3-turn GRPO is trying to learn from rollouts where 40% of turn-3 responses are not even parseable.

Why this works: right now 3-turn GRPO is dominated by "can you even emit JSON on turn 3." Most of the learning signal goes to format survival, not recipient logic. Single-turn GRPO gives clean, dense signal: valid JSON, schema compliance, To/CC split. Then SFT teaches persistence, repeat the behavior across turns without needing RL to solve long-horizon formatting from scratch.

The caveat: SFT-ing on rollouts that are only moderately correct (To/CC confusion but still some reward) means distilling the model's own biases into the multi-turn behavior. "Reply-to bias" and "all-in-To" get baked in as learned patterns. So for the SFT data, better to use ground truth trajectories (the dataset already has answer_1/2/3), or filter rollouts very strictly. Ground truth is the safer option. The training example is just the full conversation: user gives roster + email, assistant replies with the GT JSON, repeat for all three turns. This directly teaches "every turn ends in clean JSON" and "keep doing it across turns."

A practical recipe:

  • Phase A: GRPO warmup on max_turns=1. Same environment, just single-turn. Make format correctness strongly rewarded. Goal is ~99% valid JSON and decent To/CC.
  • Phase B: SFT on multi-turn GT data. Build training examples from the dataset's ground truth answers. Full 3-turn conversations with clean JSON on every turn. This teaches the model to maintain format across turns. Can mix in a small fraction of high-quality model rollouts to match the model's own style, but GT should be the backbone.
  • Phase C: GRPO again on max_turns=2 then 3. Now the model can survive multi-turn formatting, so GRPO has room to actually optimize To/CC placement across turns. SFT taught stability and imitation, GRPO teaches policy optimization.

Going the rollout-SFT route instead of GT means filtering hard. Only keep rollouts where: valid JSON on all turns, keys are exactly to, cc, bcc with list values, no sender address in outputs, To/CC scores above a threshold (say to_correct >= 0.8 and cc_correct >= 0.6), and no extra text outside the JSON. Otherwise you end up distilling exactly the errors you are trying to remove.

None of this requires a prompt contract. It is all on the environment and training side: curriculum, reward shaping, SFT sequencing. The prompt stays minimal.

Formatting as a gating condition. One implication of the 0.6B evals is that formatting is not just presentation; it is a gating condition for the rest of the reward. When the model fails to emit valid JSON, or uses names instead of email addresses, the rollout receives little or no useful recipient-placement signal even if the underlying reasoning is partly correct. That suggests adding a small auxiliary formatting reward — not as the main objective, but as a way to keep the model in the part of the output space where To/CC/BCC learning becomes possible.

There are two separable format signals here. The first is schema survival: is there valid JSON with the right keys and list values? The second is address format compliance: are the entries actual email addresses rather than names? Both are clean, binary, and much less ambiguous than To versus CC. That is exactly why they are attractive as auxiliary rewards.

The weight should stay modest: strong enough to reduce format collapse, but weak enough that recipient placement remains the dominant source of reward. The formatting reward exists to stop RL from wasting signal on avoidable parse failures, not to become the main objective. If overweighted, the model could learn the easy part — valid JSON, correct keys, email-looking strings — without improving the actual routing logic. So the reasoning is curriculum, not reward hacking: first stabilize the output contract, then optimize the harder routing behavior.

Step 1 reward (0.040) is much lower than the pre-training eval baseline (0.253). I suspect this is normal in RL post-training: train/reward at step 0 is the reward of freshly sampled completions under the RL rollout setup, not the headline eval score. The two measurements differ in several ways. Training uses temperature=1.0 with unconstrained sampling for GRPO diversity, which produces higher-entropy, more exploratory completions than the model's usual decoding. Training reward is a batch average over 512 sampled rollouts, not a stable model-wide score. The model did not start worse than baseline in a contradictory way; the two numbers come from different measurement setups.

There is a deeper reason the gap is so large. Schema validity is not just 10% of the reward — it is an access condition for the recipient-placement reward. In score_turn, To/CC/BCC receive zero unless the output parses as JSON with exactly the keys {to, cc, bcc}. So early in training, most rollouts fail before the model can earn meaningful semantic credit. At step 1, only ~18% of rollouts pass this schema gate. Under the eval decode, schema validity is already near-perfect (format_correct = 1.0 on the baseline); the remaining format issue is mostly names-versus-emails, which is penalized separately by email_format and by Jaccard mismatch against the email-address ground truth.

This was not a problem — it was a strong shaping choice. The gate created a natural curriculum: the model learned format first (steps 1-20) because it was the only way to unlock any reward at all. Once format reached 1.0 by step ~25, the gate got out of the way and the full To+CC signal became visible to the optimizer. It would only be a problem if the model never escaped the format phase, but the curves show the opposite.

Over 100 steps reward rose from 0.040 to 0.674. The most important gains were in recipient placement: to_correct reached 0.800 and cc_correct reached 0.629. Format was effectively solved: format_correct reached 1.0 by step 26 and email_format reached 0.999 by the end. On training-rollout metrics, the 0.6B model exceeded GPT-4.1-mini on To and CC placement, with overall reward also ending above the GPT-4.1-mini reference line. However, these are training-time numbers, not held-out results.

Training curves.

What happened. The training had three distinct phases. In the first ~20 steps, the model learned formatting: valid JSON with email addresses instead of names. format_correct went from 0.18 to 1.0 and email_format from 0.17 to 0.98. During this phase, recipient placement barely moved. In steps 20–50, with formatting solved, the reward signal could focus on To/CC placement. To climbed from 0.15 to 0.50, CC from 0.25 to 0.40. In steps 50–100, both metrics continued climbing: To reached 0.80 and CC reached 0.63.

The format scaffold worked as designed. It occupied the first 20 steps of training, then became invisible (both at 1.0) and let the real task take over. Without it, those first 20 steps would have been wasted on rollouts where format failures masked recipient-placement signal.

Completions also got shorter: from ~500 tokens to ~230 tokens by step 100. The model learned to produce less thinking and more direct JSON output. This made generation faster too — wall clock per batch dropped from 55s to 22s.

bcc_correct decreased over training and remained low. Under the current rubric, BCC has low weight and sparse positive signal, so the policy had little incentive to optimize it aggressively. This is best interpreted as "BCC remained undertrained" rather than as evidence for any specific BCC strategy.

Reasoning about the results.

The single-turn result (0.710 on unseen data, beating GPT-4.1-mini at 0.486) is strong, but what matters more is understanding what the model learned and what it did not. Three things stand out.

First, the model learned To/CC distinction — the core skill the environment was designed to train. GPT defaults to "everyone in To," which is a safe general-purpose heuristic but wrong for this task. The trained model learned that To means "action owner" and CC means "kept in the loop," and it applies this consistently. On unseen examples from the same synthetic distribution, the model still applies the To/CC distinction correctly, which is consistent with learning the routing policy rather than memorizing individual rows.

Second, the model learned conciseness without being explicitly rewarded for it. Thinking tokens dropped 5x. This is an emergent effect of GRPO: shorter completions leave less room for the model to drift or second-guess itself, and the reward only depends on the final JSON. So the optimization pressure implicitly favors directness. This is worth noting because it suggests that RL training can shape behaviors that are not directly in the rubric — a double-edged sword that is useful here but could be harmful in other settings.

Third, the model did not learn a useful BCC policy. Its test-set score (0.036) is lower than what simple abstention would produce (~0.12), so the picture is messier than "learned to leave BCC empty." The rubric gives BCC low weight and sparse positive signal, creating poor incentive to attempt it. If BCC matters, the rubric needs to change. This is a good example of reward shaping limitations: the model optimizes what you reward, which may not be what you want.

The multi-turn collapse (format drops to 71% on turn 3) is the most actionable finding. The model was never trained on multi-turn, so it is unsurprising, but it means the current checkpoint cannot be deployed as-is for multi-turn scenarios. The fix is straightforward: Phase B (SFT on ground-truth multi-turn conversations) would teach the model to maintain format across turns, and Phase C (multi-turn GRPO) would then optimize placement on turns 2 and 3.

Possible future directions.

Phase B + C. SFT on the dataset's ground-truth answers (full 3-turn conversations with clean JSON) to teach format persistence, then GRPO on max_turns=2 and 3. The single-turn placement quality should transfer, and multi-turn format should be learnable from supervised examples.

BCC reward redesign. The current rubric makes BCC abstention optimal. To actually train BCC prediction, either upweight it significantly (e.g. 0.30) or add a separate binary reward for "correctly predicted non-empty BCC when ground truth is non-empty." The model needs a strong enough signal that attempting BCC is worth the risk of getting it wrong.

To/CC swap analysis. The remaining failures are all To/CC swaps. This might be fixable by adjusting the data: making the "primary action owner" even more explicit in the email text, or adding a dedicated reward for "is the To person the one being directly tasked in the email." The current Jaccard reward treats all placement errors equally — a more targeted signal might help.

VIILearnings

How load_environment receives arguments. The verifiers framework calls load_environment(env_id=..., **env_args) where env_args comes from the CLI or config file. Any keyword argument defined in load_environment - like max_turns, dataset_name, or dataset_split - can be overridden at eval time without touching the environment code. The **kwargs catch-all absorbs anything extra the framework passes. This means the same environment supports single-turn eval (max_turns=1) or full 3-turn threads (max_turns=3) just by changing the CLI invocation. The environment itself does not need separate single-turn and multi-turn implementations.

Editable installs: code is live, metadata is not. With pip install -e ., Python imports the source files directly, so code changes (new scoring logic, prompt edits) take effect immediately. But package metadata like the version string is baked into .dist-info at install time. Anything that reads the version via importlib.metadata.version() will see the old number until you reinstall. After bumping the version in pyproject.toml, run uv pip install -e . to update the metadata. This is why the eval viewer can run new code but still tag results with the old version.

Small models output dicts, not strings. When a 0.6B model sees "reply with JSON", it sometimes wraps email addresses in objects like [{"email": "alice@..."}] instead of plain strings. Calling set() on that list crashes with unhashable type: 'dict'. The fix: filter out non-string elements and cast the rest with str(). Always assume the model will find creative ways to break your parser.
