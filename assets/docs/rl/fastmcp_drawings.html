FastMCP, Drawings, and More

RL environment where a VLM learns to draw. Inspired by Printing Machines — models use drawing tools, see the canvas each turn, and iteratively produce images. Current frontier models fail badly at this. We can train on it.

Loop

Multi-turn, vision-in-the-loop. Each turn: model sees target image + current canvas, calls a drawing tool, canvas updates, screenshot fed back.

Turn 1: [target + blank canvas]  → model calls draw_line(...)   → screenshot
Turn 2: [target + canvas]        → model calls draw_spline(...) → screenshot
Turn 3: [target + canvas]        → model calls draw_curve(...)  → screenshot
...
Turn N: model calls stop() → score against target

Tools

FastMCP server exposes drawing primitives. The model only sees these — no raw canvas access.

draw_line(x1, y1, x2, y2)
draw_spline(points[])
draw_polyline(points[])
draw_curve(x1, y1, cx1, cy1, cx2, cy2, x2, y2)    # bezier
undo()
update_notes(notes)                                  # 20k-token scratchpad
stop()

Splines and bezier curves are native to HTML Canvas. Reimplementing them in PIL would be fighting the problem — use a real canvas.

Stack

No Docker, no prime sandboxes. env_response manages everything.

Model (VLM)
  ↓ tool calls
env_response
  ↓ stdio
FastMCP server (drawing tools)
  ↓ executes on
HTML Canvas (in WebContainer / headless browser)
  ↓ screenshot
Playwright
  ↓ PNG
env_response returns image message to VLM

WebContainers

WebContainers run Node.js in WASM — millisecond startup, no Docker, per-rollout isolation without heavyweight containers. The FastMCP canvas app is a web app, which is exactly what WebContainers are for.

Each rollout gets its own WebContainer with its own canvas. Starts instantly, dies cleanly, no port conflicts, no shared state.

Lifecycle

setup_state:
    1. Spin up WebContainer (WASM, fast)
    2. Run FastMCP canvas app inside it
    3. Connect Playwright for screenshots
    4. Load target image into state

env_response:
    1. Parse tool call from model message
    2. Route to FastMCP over stdio
    3. Canvas executes the draw command
    4. Playwright screenshots the canvas
    5. Return [screenshot + target] as image message

cleanup:
    Tear down WebContainer + Playwright

Scoring

Compare final canvas to target. Options:

  • SSIM — structural similarity, catches shape and layout
  • Pixel MSE — simple, noisy on small misalignments
  • Perceptual — LPIPS or similar, matches human judgement better but needs a pretrained net
  • Hybrid — weighted combination. SSIM for structure, pixel for precision

The Printing Machines benchmark found that "small perceptual or execution mistakes compound over time." A good reward function should give partial credit for progress, not just score the final frame.

Rerun

Hook up Rerun to stream rollouts live. Each rollout logs its canvas state, tool calls, and scores to a Rerun recording. You get a link, open it, and watch the drawing build up stroke by stroke in real time.

env_response:
    ...
    4. Playwright screenshots the canvas
    5. rr.log("canvas", rr.Image(screenshot))
    6. rr.log("tool_call", rr.TextLog(f"{tool_name}({tool_args})"))
    7. Return image message to VLM

During training you'd see every rollout's drawing process — which strokes the model chose, where it went wrong, how it recovered (or didn't). Compare rollouts side by side: the one that scored 0.9 vs the one that scored 0.2. See exactly where they diverge.

Also useful for debugging reward functions — watch a rollout that scored low and check if the reward is wrong or the model is. Beats staring at JSON logs.

Open Questions

  • VLM training cost — vision models are heavier than text-only. vLLM serving a VLM needs more GPU memory.
  • Screenshot latency — Playwright screenshot per turn adds time. Acceptable if turns are seconds, not milliseconds.
  • Task generation — need a dataset of target images. Vector drawings, line art, simple shapes to start. Complexity scales with model capability.
  • Partial credit — per-turn reward vs end-of-rollout? Per-turn is denser signal but harder to compute fairly.
