FastMCP, Drawings, and More

RL environment where a VLM learns to draw. Inspired by Printing Machines — models use drawing tools, see the canvas each turn, and iteratively produce images. Current frontier models fail badly at this. We can train on it.

Loop

Multi-turn, vision-in-the-loop. Each turn: model sees target image + current canvas, calls a drawing tool, canvas updates, screenshot fed back.

Turn 1: [target + blank canvas]  → model calls draw_line(...)   → screenshot
Turn 2: [target + canvas]        → model calls draw_spline(...) → screenshot
Turn 3: [target + canvas]        → model calls draw_curve(...)  → screenshot
...
Turn N: model calls stop() → score against target

Tools

FastMCP server exposes drawing primitives. The model only sees these — no raw canvas access.

draw_line(x1, y1, x2, y2)
draw_spline(points[])
draw_polyline(points[])
draw_curve(x1, y1, cx1, cy1, cx2, cy2, x2, y2)    # bezier
undo()
update_notes(notes)                                  # 20k-token scratchpad
stop()

Splines and bezier curves are native to HTML Canvas. This is why we use a real Canvas instead of a Python graphics library.

Architecture

The FastMCP server is the interface. Playwright is the sandbox — a headless Chromium that runs the Canvas, renders drawings, and takes screenshots. The browser is the sandbox.

verifiers (Python)
  ↓ stdio
FastMCP server (Python)
  ↓ controls
Playwright (headless Chromium)
  ↓ runs
HTML Canvas (ui:// resource)
  ↓ screenshot
base64 PNG → back to VLM as tool response

FastMCP tools are the policy — predefined operations with typed inputs. The model can’t inject code, access the filesystem, or escape the Canvas. Capability-scoped by design.

FastMCP Apps

Each drawing tool is linked to a ui:// resource via AppConfig. The ui:// resource is the Canvas HTML — same code used for both training and viewing.

  • Training — Playwright renders the ui:// HTML headlessly. Screenshots go to the VLM as ImageContent in the tool response.
  • Watching — human opens a client that supports MCP Apps (or connects a browser). Same Canvas, live, no extra code.
  • Human-in-the-loop — the App UI can call back to the server via callServerTool(). A human viewer can intervene: correct a stroke, rate the drawing, add hints. Tool visibility controls who can call what — ["model"] only, ["app"] only, or both.

One HTML file serves three purposes: training renderer, live viewer, HITL interface.

Playwright as Sandbox

Playwright gives us a headless Chromium that works on GPU servers with no display. The Canvas runs inside it with full browser sandboxing — CSP, same-origin, process isolation. 30 years of browser security infrastructure for free.

ModeWhat happens
headless=TrueGPU server, training. No window. Screenshots only.
headless=FalseYour laptop, development. Browser window pops up, watch live.
Video recordingrecord_video_dir="./videos" — one line, get mp4 per rollout.

The browser is not the environment the agent controls (that’s a web agent). The browser is where the Canvas lives. The model talks through FastMCP tools, never touches the browser directly.

Why Not WebContainers?

WebContainers (StackBlitz) is browser-only — it needs Service Workers and SharedArrayBuffer. No browser on a GPU server means no WebContainers. Playwright provides the headless browser context that WebContainers would need anyway, making WebContainers redundant.

WASM sandboxes (Wasmer, Wasmtime) work headlessly but don’t have Canvas. Canvas needs a browser. Playwright is that browser.

Lifecycle

setup_state:
    1. Launch Playwright (headless Chromium)
    2. Load Canvas HTML page
    3. Start FastMCP server over stdio
    4. Load target image into state

env_response:
    1. Parse tool call from model message
    2. Route to FastMCP → Playwright executes draw command on Canvas
    3. Screenshot the Canvas
    4. Return [screenshot + target] as image message to VLM

cleanup:
    Close Playwright browser context

Fresh per rollout. Canvas starts blank, Playwright browser context is disposable. No state leaks between rollouts.

Scoring

Compare final canvas to target. Options:

  • SSIM — structural similarity, catches shape and layout
  • Pixel MSE — simple, noisy on small misalignments
  • Perceptual — LPIPS or similar, matches human judgement better but needs a pretrained net
  • Hybrid — weighted combination. SSIM for structure, pixel for precision

The Printing Machines benchmark found that “small perceptual or execution mistakes compound over time.” A good reward function should give partial credit for progress, not just score the final frame.

Monitoring

Rerun

Hook up Rerun to stream rollouts live. Each rollout logs its canvas state, tool calls, and scores to a Rerun recording.

env_response:
    ...
    3. Screenshot the Canvas
    4. rr.log("canvas", rr.Image(screenshot))
    5. rr.log("tool_call", rr.TextLog(f"{tool_name}({tool_args})"))
    6. Return image message to VLM

Compare rollouts side by side: the one that scored 0.9 vs the one that scored 0.2. See exactly where they diverge. Also useful for debugging reward functions — watch a rollout that scored low and check if the reward is wrong or the model is.

Playwright Video

One-line rollout recording: browser.new_context(record_video_dir="./videos"). Every rollout becomes an mp4. Review later, share, or build a dataset of drawing trajectories.

Open Questions

  • VLM support in verifiers — does the trainer/GRPO pipeline handle image observations in the conversation? vLLM serving a VLM needs more GPU memory.
  • Screenshot latency — Playwright screenshot per turn adds time. Acceptable if turns are seconds, not milliseconds.
  • Task generation — need a dataset of target images. Vector drawings, line art, simple shapes to start. Complexity scales with model capability.
  • Partial credit — per-turn reward vs end-of-rollout? Per-turn is denser signal but harder to compute fairly.
