Training Architecture: Who Does What                                                                

Four pieces, each with one job:                                                                     

vLLM (Inference Server)                                                                             

 • Hosts the model as an OpenAI-compatible API                                                      
 • Serves completions when asked                                                                    
 • Accepts weight updates from the trainer via NCCL                                                 

Verifiers (Environment + Scoring)                                                                   

 • Calls vLLM to generate completions                                                               
 • Manages multi-turn conversation loops (prompt → response → environment feedback → response → ...)
 • Scores rollouts with rubrics                                                                     
 • Returns rollouts with rewards                                                                    

Trainer (Weight Updates)                                                                            

 • Receives rollouts and rewards from verifiers                                                     
 • Computes advantages from the rewards (using whatever method the trainer chooses - GRPO,          
   REINFORCE, etc.)                                                                                 
 • Computes loss, updates model weights                                                             
 • Pushes new weights back to vLLM                                                                  
 • Never serves completions, never scores anything                                                  

Orchestrator (Glue)                                                                                 

 • Lives inside the trainer (orchestrator.py)                                                       
 • Calls env.generate() on verifiers with the vLLM client                                           
 • Processes the results into microbatches (token IDs, masks, logprobs, advantages)                 
 • Feeds microbatches to the trainer's training loop                                                

The Loop                                                                                            

                                                                                                    
 vLLM serves model                                                                                  
     ↓                                                                                              
 Verifiers calls vLLM, gets completions, scores them                                                
     ↓                                                                                              
 Orchestrator packages scored rollouts into microbatches                                            
     ↓                                                                                              
 Trainer computes advantages, does weight update                                                    
     ↓                                                                                              
 Weight sync pushes new weights to vLLM                                                             
     ↓                                                                                              
 repeat                                                                                             
                                                                                                    

Where Advantages Get Computed                                                                       

This depends on which trainer you use:                                                              

t2f-trainer - computes its own advantages from raw rewards in orchestrator.py. Currently uses GRPO  
(reward - group_mean), but we own the formula and can swap in std normalization, KL penalty, or     
different algorithms without touching verifiers.                                                    

prime-rl, SkyRL, rLLM, etc. - same idea. Verifiers only returns rollouts + reward scores. The       
trainer computes its own advantages using whatever algorithm it wants.                              

Note: verifiers still computes and attaches its own advantage field in rubric.py, but t2f-trainer   
ignores it and uses the raw reward values instead.                                                  

Why Verifiers is Trainer-Agnostic (and Where It Leaks)                                              

Verifiers just needs an OpenAI-compatible endpoint. It doesn't care who's hosting it or who's       
consuming the results. Any trainer can plug in - it just needs to:                                  

 1 Spin up vLLM (or similar) with the model                                                         
 2 Point verifiers at it                                                                            
 3 Consume the rollouts and rewards                                                                 
 4 Compute advantages, update weights, sync back to vLLM                                            

The coupling that exists anyway. Verifiers doesn't import or depend on any trainer. But a trainer   
can't just blindly consume a reward scalar - it needs to understand the multi-turn trajectory       
structure verifiers produces. Specifically:                                                         

 • It needs to call env.generate() to trigger the rollout loop (the trainer controls timing because 
   it owns the weights and must coordinate weight sync around generation)                           
 • It needs to parse trajectory steps to build correct loss masks (model tokens = 1, prompt/env     
   response tokens = 0)                                                                             
 • It needs to handle weight sync timing - can't update vLLM weights mid-generation                 

The orchestrator is the adapter layer that bridges this gap. It speaks verifiers on one side        
(trajectories, states, tokens) and speaks trainer on the other (microbatches, input_ids, loss_masks,
advantages). Verifiers is trainer-agnostic in that it has no trainer dependency, but any trainer    
that wants to use it needs to build an orchestrator that understands verifiers' output format.      

Two Relationships with vLLM                                                                         

The trainer and verifiers talk to vLLM for different reasons:                                       

 • Verifiers → vLLM: "generate completions for these prompts" (OpenAI-compatible API, during        
   rollouts)                                                                                        
 • Trainer → vLLM: "here are updated weights" (NCCL GPU-to-GPU broadcast, between steps)            

The trainer coordinates the two - it waits for verifiers to finish generating, syncs weights, then  
tells the orchestrator to kick off the next batch. If verifiers queried vLLM freely, completions    
could be generated with stale weights or during a weight update.
