ORCHESTRATOR

IIOne Training Step

What follows describes a synchronous training step: generate, train, sync, repeat. Production trainers like prime-rl use asynchronous off-policy training, where generation and training overlap and rollouts may come from a policy several steps behind the current one. The concepts (rollouts, advantages, ratio, loss) are the same, but the timing and staleness constraints differ.

The trainer calls env.generate() on the environment in verifiers. Verifiers drives the rollout loop, calling the inference server for completions, running env_response() between turns, repeating until done, then scores the rollout with its rubric, which may consist of multiple reward functions. The trainer collects the results, computes advantages from the rewards (however it chooses, whether standard GRPO, Dr.GRPO, etc.), packages microbatches, re-evaluates the same tokens under the current policy, computes loss, updates weights, and syncs back to the inference server.

One Training Step

  • Microbatch. Grouping matters for computing advantages (e.g. GRPO compares rollouts within the same prompt group). But once each rollout has its advantage scalar, the group doesn't matter anymore. The trainer just needs (tokens, logprobs, advantage) per rollout to compute loss. Microbatching is a knob: it controls how many rollouts you process at once per GPU before accumulating gradients. Smaller microbatches use less memory, larger ones are more efficient.
  • Loss. For each microbatch, the trainer re-runs the same token sequences through the current policy to get fresh logprobs. It then compares these against the logprobs from generation time via the importance ratio: ratio = exp(trainer_logprob - sampling_logprob). The loss is -ratio × advantage, masked so only completion tokens contribute. Positive advantage means negative loss: gradient descent pushes the token probability up. Negative advantage, positive loss: pushes it down. Gradients accumulate across all microbatches, then one optimizer step updates the weights.
    Good token Bad token
    $\log\pi_{\text{old}}$ -0.30 -1.20
    $\log\pi_\theta$ -0.35 -1.10
    advantage +0.40 -0.40
    ratio 0.95 1.10
    loss -0.38 push up +0.44 push down
  • Clipping. The ratio can drift if the policy has shifted since generation. In verifiers-rl, tokens with a ratio outside [0.125, 8.0] are dropped from the loss. In a synchronous loop this almost never fires because the ratio stays close to 1. In async setups like prime-rl, rollouts can come from a policy several steps behind, so clipping is part of the intended design, not just a safety net.
  • Credit assignment. In many GRPO-style setups, every token in a completion gets the same advantage (sequence-level reward broadcast to all tokens). This is coarse, but over many steps the signal averages out: tokens that consistently appear in good completions get reinforced, bad ones get suppressed. The framework can support finer-grained token-level signals too. This is also why GRPO needs reward diversity. If all rollouts for a prompt get the same reward, all advantages are zero, and no learning happens for that group.

IIIWeight Sync

In a synchronous loop, generation and weight sync are mutually exclusive. You can't sync while the inference server is generating (corrupts in-flight inference) and you can't generate during sync (mixed weights). The cycle is: finish generating, train, sync, start generating. Production async trainers like prime-rl relax this with in-flight weight updates.

Timeline

Weight sync, and doing synchronous RL training in general, has been one of the main things to optimize. The generate-train-sync cycle means the trainer sits idle during generation and the inference server sits idle during training. That's why we see async RL, where generation and training overlap.

Verifiers-rl, for example, is synchronous and has this problem. It's hackable and good for learning, but the idle time adds up. Production trainers like prime-rl attack this directly with async generation, overlapping rollouts with training so neither side sits idle. This is one of the biggest active research problems in RL training infrastructure.

The importance ratio from the loss section measures how much the current policy has shifted since the rollout was generated. In a strict synchronous loop, the ratio starts at 1 on a freshly collected batch (same weights generate and train on it). In async setups like prime-rl, rollouts may come from a policy up to max_async_level steps behind, so the ratio can already differ from 1 before any training happens on that batch. Either way, the "old policy" logprobs are frozen at generation time, and the ratio exists to correct for the gap between the policy that generated the tokens and the policy being trained.

IVTrainer-Agnostic

Verifiers has no trainer imports. It needs one thing: an OpenAI-compatible endpoint for generation. Any trainer can plug in, it just needs to build a controller/orchestrator that:

  • Calls env.generate() with the vLLM client
  • Parses the trajectory structure: token IDs, logprobs, turn boundaries
  • Builds loss masks: model output = 1, prompt/env response = 0
  • Coordinates weight sync around generation

Every trainer that supports verifiers (prime-rl, t2f-trainer, Tinker, SkyRL, rLLM) built this adapter independently. The env and reward functions are portable. The orchestrator glue is not.

t2f-trainer is verifiers-rl, modified: some things added, some things fixed, but in essence it's verifiers-rl. The point stands across trainers. t2f-trainer, prime-rl, SkyRL, rLLM all take the rollouts and rewards from verifiers and compute their own advantages. The trainer just wants rollouts and rewards, nothing more.
