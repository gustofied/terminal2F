TOPOLOGY & WORKINGS

ITopology

Topology

Channel Direction Purpose Protocol
A Verifiers → vLLM Generate completions during rollouts OpenAI HTTP API
B Trainer → vLLM Push updated weights between steps NCCL GPU-to-GPU
vLLM Hosts the model as an OpenAI-compatible API. Serves completions when asked. Accepts weight updates from the trainer via NCCL.
VERIFIERS Calls vLLM to generate completions, manages multi-turn conversation loops, scores rollouts with rubrics, returns rollouts with rewards.
TRAINER Receives rollouts and rewards. Computes advantages (GRPO, REINFORCE, whatever it chooses). Computes loss, updates weights, pushes new weights back to vLLM. Never serves completions, never scores anything.
ORCHESTRATOR Lives inside the trainer. Calls env.generate() with the vLLM client. Processes results into microbatches (token IDs, masks, logprobs, advantages). Feeds microbatches to the training loop.

IITraining

One full cycle. The orchestrator prepares what the trainer needs: rollouts, advantages, microbatches. The trainer re-evaluates the same tokens under the current policy, computes loss, and updates weights. Then syncs to vLLM so the next batch generates with the new policy.

Steps

One step processes one batch. A batch is all your rollouts: say 5 examples from the dataset, 3 rollouts each, so 15 rollouts total. Advantages are computed per group before anything hits the trainer. After that each rollout carries its own advantage and the trainer doesn't need to know which group it came from. Microbatches just split those 15 rollouts into smaller chunks that fit in GPU memory. The trainer processes them one by one, accumulates gradients, then does a single optimizer step at the end.

IIIMicrobatch

What the trainer actually receives. Four fields per training example, packaged by the orchestrator.

aTokens

In LLMs, a token is an integer index into a vocabulary table. The tokenizer chops text into subword pieces based on frequency:

"Hello world" → ["Hello", " world"] → [15496, 995]

Built via BPE (Byte Pair Encoding): start with individual bytes, repeatedly merge the most frequent adjacent pair until ~100k vocabulary entries. Common words get one token, rare words get split:

Text Token IDs
"John" [2198] common, one token
"Zygmunt" [31849, 4452, 1628] rare, three tokens

vLLM generates a completion and returns both forms in a single response. No re-tokenization needed. Token IDs go to the trainer, text goes to the reward functions.

vLLM RESPONSE 
prompt_ids     = response.prompt_token_ids       # [1042, 553, 8821]
completion_ids = response.choices[0].token_ids    # [4417, 229, 1105]
logprobs       = [t.logprob for t in content]     # [-0.3, -1.2, -0.1]
text           = response.choices[0].message.content

bFields

Field What it is
input_ids Full token sequence, prompt + completion concatenated. The trainer needs the full sequence because each token's probability depends on everything before it.
loss_mask Same length, binary. 0 = prompt (context only), 1 = completion (train on this). In multi-turn, env responses between turns also get masked to 0.
sampling_logprobs The log probability vLLM assigned to each completion token when it generated them. The "old policy" probabilities. Zeros for prompt tokens.
advantages A single scalar (reward minus group mean), repeated for every token. Computed by the orchestrator from raw rewards.
PROMPT COMPLETION
input_ids 1042 553 8821 4417 229 1105
loss_mask 0 0 0 1 1 1
logprobs 0.0 0.0 0.0 -0.3 -1.2 -0.1
advantages 0.3 0.3 0.3 0.3 0.3 0.3

Logprobs are the log of the softmax of the raw logits. Open-weight models on vLLM give full access to logits, so logprobs are computed directly.

LOGITS → LOGPROBS 
logits:   [2.1, 0.5, -1.3, ...]      raw scores for every vocab token
              ↓ softmax
probs:    [0.74, 0.15, 0.02, ...]     probabilities (sum to 1)
              ↓ log
logprobs: [-0.3, -1.9, -3.9, ...]     stored for the sampled token

Advantages are computed in the orchestrator from raw rewards:

ADVANTAGE COMPUTATION 
for g in range(0, len(raw_rewards), rollouts_per_example):
    group      = raw_rewards[g : g + rollouts_per_example]
    group_mean = sum(group) / len(group)
    advantages.extend(r - group_mean for r in group)

IVLoss

The trainer runs one forward pass on input_ids, gets its own logprobs, then computes the policy ratio against the sampling logprobs from generation time.

Policy Ratio & Loss 
ratio = exp(trainer_logprob - sampling_logprob)
loss  = -ratio × advantage

$\pi_\theta$ is the trainer's current policy. $\pi_{\text{old}}$ is the policy that generated the completion (vLLM at sampling time). The ratio measures how much the policy has shifted since generation. The loss_mask ensures only completion tokens contribute.

aDirection

Advantage Loss Effect
positive negative gradient descent increases $\log\pi$ – token becomes more probable
negative positive gradient descent decreases $\log\pi$ – token becomes less probable

bWorked Example

Two tokens from two completions of the same prompt. Same formula, opposite outcomes.

Good – "alice" Bad – "bob"
$\log\pi_{\text{old}}$ -0.30  $p \approx 0.74$ -1.20  $p \approx 0.30$
$\log\pi_\theta$ -0.35  $p \approx 0.70$ -1.10  $p \approx 0.33$
advantage +0.40 -0.40
ratio 0.95  $e^{-0.05}$ 1.10  $e^{+0.10}$
loss -0.38  push up +0.44  push down

The gradient on each completion token: $\frac{\partial \mathcal{L}}{\partial \log\pi} = -A \cdot r$. The advantage controls direction and magnitude. The ratio corrects for policy drift since generation.

cClipping

The ratio can get extreme if the policy has shifted a lot since generation. PPO clipping caps it:

PPO Clip  ($\varepsilon = 0.2$) 
clipped = clip(ratio, 1-ε, 1+ε)
loss    = -min(ratio × A, clipped × A)

This prevents any single update from moving weights too aggressively. For positive advantages, it caps large probability increases. For negative advantages, it caps large decreases. The model can only move so far per step.

dCredit Assignment

Every token in a completion gets the same advantage value. If the completion scored well, all its tokens get reinforced – even punctuation, formatting, filler words. The model can't tell which specific tokens were responsible for the score.

This is coarse: sequence-level reward applied uniformly to all tokens. But it works. Over many training steps and many examples, the signal averages out. Tokens that consistently appear in good completions get reinforced. Tokens that consistently appear in bad ones get suppressed. The diversity within each group (some rollouts good, some bad for the same prompt) is what makes the signal informative.

This is also why GRPO needs reward diversity. If all K rollouts for a prompt get the same reward, all advantages are zero, and no learning happens for that group.

eWhy the Trainer Needs Prompt IDs

The full sequence (prompt + completion) goes into the forward pass. The model processes left-to-right: it needs to "read" the prompt tokens to build up the right hidden states before it reaches the completion tokens. Without the prompt context, the logprobs it computes on the completion tokens would be meaningless. No gradients flow through the prompt, the loss mask is 0 for all prompt tokens, but they're essential as input context.

fTwo Copies

There are two copies of the same weights in GPU memory. The trainer copy (transformers/deepspeed), where gradients flow and weights get updated. The inference copy (vLLM), which generates completions and receives weight syncs. Same architecture, same weights after sync. Two copies because generation and gradient computation have different computational patterns and can't efficiently share a single loaded model. The sync happens every training step via NCCL broadcast, not at checkpoints. Checkpoints are periodic saves to disk for crash recovery.

VWeight Sync

Generation and weight sync are mutually exclusive. You can't sync while vLLM is generating, that would corrupt in-flight inference. You can't generate during sync, you'd get mixed weights. The trainer enforces: finish generating → sync → start generating.

Timeline

Weight sync, and doing synchronous RL training in general, has been one of the main things to optimize. The generate-train-sync cycle means the trainer sits idle during generation and vLLM sits idle during training. That's why we see async RL, where generation and training overlap.

VITrainer-Agnostic

Verifiers has no trainer imports. It needs one thing: an OpenAI-compatible endpoint for generation. Any trainer can plug in, it just needs to build an orchestrator that:

  • Calls env.generate() with the vLLM client
  • Parses the trajectory structure: token IDs, logprobs, turn boundaries
  • Builds loss masks: model output = 1, prompt/env response = 0
  • Coordinates weight sync around generation

Every trainer that supports verifiers (prime-rl, t2f-trainer, Tinker, SkyRL, rLLM) built this adapter independently. The env and reward functions are portable. The orchestrator glue is not.

t2f-trainer is verifiers-rl, modified: some things added, some things fixed, but in essence it's verifiers-rl. The point stands across trainers. t2f-trainer, prime-rl, SkyRL, rLLM all take the rollouts and rewards from verifiers and compute their own advantages. The trainer just wants rollouts and rewards, nothing more.

As of writing, verifiers-rl was still a little attached to verifiers itself: it took the advantage directly from the rubric. t2f-trainer ignores that and computes its own, just as prime-rl and SkyRL do. This is what makes the design clean. Any trainer can plug in:

  • Spin up vLLM (or similar) with the model
  • Point verifiers at it
  • Consume the rollouts and rewards
  • Compute advantages, update weights, sync back to vLLM
