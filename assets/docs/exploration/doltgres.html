Doltgres

Doltgres is a Postgres-wire server built on the Dolt engine. It lets Postgres clients connect normally while exposing Dolt's version-control model through SQL. The core idea is Git for database state: you can branch, diff, merge, and commit database changes, with row-level history underneath. Every transaction can be turned into a versioned commit. An agent needs a safe copy of the world it is about to change — not a sandbox, not a container, but a branch.

IWhy it matters for agents

Two layers of need emerge when agents interact with databases:

  • RL layer — forkable state, fast reset, isolated concurrent worlds, diffable outcomes, replayability. The database as a training environment.
  • Product layer — human-readable versioned history, debugging, benchmarking, artifacts. The database as an auditable record.

Doltgres handles both because branching is cheap (no VMs, no containers, just a logical fork inside the same process) and the history is rich (row-level diffs, commit messages, per-row timelines). The primitive both layers share: a safe copy of the world before you change it.

II.aLearnings: server

The engine underneath is Dolt, which thinks in MySQL. Doltgres translates the Postgres wire protocol into that engine. Dolt docs and examples are MySQL-flavored, but the same concepts apply — you just adjust the syntax.

To see what configuration is available, run doltgres -config-help. This prints the full config.yaml reference:

yaml 
log_level: info                          # debug | info | warn | error

encode_logged_query: false               # encode SQL in logs (binary safety)

behavior:
  read_only: false                       # reject all writes if true
  dolt_transaction_commit: false         # auto dolt_commit on every tx

user:
  name: postgres
  password: password

listener:
  host: localhost
  port: 5432
  read_timeout_millis: 28800000          # 8 hours
  write_timeout_millis: 28800000         # 8 hours
  allow_cleartext_passwords: false

data_dir: ~/doltgres/databases            # where databases live on disk

cfg_dir: .doltcfg
privilege_file: .doltcfg/privileges.db   # user privileges
auth_file: .doltcfg/auth.db              # authentication data
branch_control_file: .doltcfg/branch_control.db  # branch permissions

The interesting ones for agents:

  • dolt_transaction_commit - when true, every SQL transaction automatically becomes a Dolt commit. Agents don't need to call dolt_commit() explicitly. Can also be set per-session via SET dolt_transaction_commit = 1; so only that connection auto-versions, not every admin query.
  • branch_control_file - branch-level permissions. Restrict which agents can write to which branches.
  • read_only - give agents read-only access to main while they write to their own branch on a separate connection.

II.bLearnings: commits

A transaction is a group of operations that either all succeed or all fail - all or nothing. Without transactions, if an error occurs mid-way, the database could end up in an inconsistent state. This is atomicity, the A in ACID.

In normal databases, "commit" only means finalizing a transaction. There's no standalone concept of committing outside of that.

Inside a transaction, each INSERT, SELECT, UPDATE, DELETE is a statement. Statements are the verbs. Tables are the nouns. Schemas define the shape of the nouns. The hierarchy:


text 
Transaction
  └── Statement  (INSERT INTO employees ...)
  └── Statement  (UPDATE accounts SET ...)
  └── Statement  (SELECT * FROM ...)
  └── COMMIT or ROLLBACK

Dolt adds a layer on top. A Dolt commit is a permanent versioned snapshot - like a git commit. It has a hash, a message, an author, a timestamp. You can go back to it, diff against it, branch from it. It lives forever in dolt_log. Multiple database transactions can happen between Dolt commits:

text 
Dolt commit  (versioned snapshot: hash, message, author)
  └── Transaction
  │     └── Statement
  │     └── Statement
  │     └── COMMIT
  └── Transaction
  │     └── Statement
  │     └── COMMIT
  └── dolt_commit('-am', 'description')

The bridge between the two: dolt_transaction_commit = 1. When set, every database transaction COMMIT also creates a Dolt commit. Without it, you can commit hundreds of database transactions and Dolt sees nothing - the data changes, but there is no versioned history. You would have to manually call dolt_commit() to snapshot.

When you call conn.execute("INSERT ...") in psycopg, you are just running a SQL statement. But the database always works in transactions - there is no way around it. With autocommit = True, every statement is silently wrapped in its own BEGIN/COMMIT. With autocommit off (the default), psycopg opens a transaction on the first statement and holds it open until you explicitly call conn.commit() or conn.rollback(). This means you can batch related writes and commit them as one unit - and with dolt_transaction_commit = 1, that whole batch becomes a single Dolt commit instead of N separate ones.

The dolt_transaction_commit setting controls whether Dolt automatically snapshots on every transaction commit:

false (default) - manual snapshots

text 
INSERT  →  tx commits  →  data changes ✓  →  dolt history: nothing
INSERT  →  tx commits  →  data changes ✓  →  dolt history: nothing
SELECT dolt_commit('-am', 'msg')           →  dolt history: one commit (both inserts)

You control when to snapshot. Good for admin work - keep the log clean, write meaningful commit messages.

true - automatic snapshots

text 
INSERT  →  tx commits  →  data changes ✓  →  dolt history: commit
INSERT  →  tx commits  →  data changes ✓  →  dolt history: commit

Every transaction commit creates a Dolt commit. Nothing slips through. Good for agent connections where you want full tracking. The tradeoff: the log gets noisy and commit messages are auto-generated, not meaningful.

Best of both worlds: leave it false in the server config, then SET dolt_transaction_commit = 1 only on agent connections. Your admin queries stay clean, agent writes are fully tracked.

II.cMulti-user

Multi-user works, but with workarounds. Postgres-style CREATE USER ... WITH PASSWORD corrupts privileges.db. The fix: create users MySQL-style (no WITH PASSWORD), set the password separately with ALTER USER, and reconnect between every privilege operation — the psycopg session gets corrupted after each privilege change.

The full recipe via psycopg:

python 
# each step needs its own connection (reconnect between every step)

# 1. create user (MySQL-style, NO "WITH PASSWORD")
conn.execute('CREATE USER "agent1@localhost"')

# 2. set password separately (ALTER USER is safe)
conn.execute('ALTER USER "agent1@localhost" WITH PASSWORD \'agent1pass\'')

# 3. grant database access
conn.execute('GRANT ALL ON DATABASE getting_started TO "agent1@localhost"')

# 4. grant schema access (needed to create tables)
conn.execute('GRANT ALL ON SCHEMA public TO "agent1@localhost"')

# 5. grant table access (needed for existing tables)
conn.execute('GRANT ALL ON ALL TABLES IN SCHEMA public TO "agent1@localhost"')

Why separate users matter: attribution. Each user's writes show up in dolt_log under their name. If both agents use postgres, every commit says "postgres" and you can't tell who did what. With separate users, agent1's commits show agent1@localhost and you get git-blame for your database.

When you need it: multi-agent setups, or human + agent workflows where you want to distinguish who made which changes. Single-agent RL with reset loops: one user is fine.

II.dBranches and isolation

Branches give each agent its own isolated copy of the database. Creating branches is a SQL operation:

sql 
SELECT dolt_branch('dev1', 'main');
SELECT dolt_branch('dev2', 'main');

The cleanest way to connect an agent to its branch: put the branch name directly in the connection string. No dolt_checkout() needed.

python 
# agent1 connects directly to dev1 branch
a1 = psycopg.connect(
    "host=127.0.0.1 user=agent1@localhost password=agent1pass "
    "dbname=getting_started/dev1"
)
a1.autocommit = True

# agent2 connects directly to dev2 branch
a2 = psycopg.connect(
    "host=127.0.0.1 user=agent2@localhost password=agent2pass "
    "dbname=getting_started/dev2"
)
a2.autocommit = True

Each branch behaves like its own writable database. Agent1 creates tables and inserts data on dev1, agent2 does the same on dev2, and main stays clean. Merging is a separate privileged operation your orchestrator does when the work looks good:

sql 
-- from main, merge agent1's work
SELECT dolt_merge('dev1');

This is the Cursor/PR model for databases: agents work on their branch, merging to main is a review step. The agent doesn't need permission to merge because merging isn't in its toolkit.

II.eBranch permissions (broken)

Two system tables are supposed to control branch permissions: dolt_branch_control (who can write to which branches) and dolt_branch_namespace_control (who can create which branch names). Three permission levels: admin, write, and read (everyone has read by default). Pattern matching uses LIKE-style wildcards.

In practice, we could not modify dolt_branch_control through the Postgres wire protocol. Simple INSERTs failed with a MySQL-to-Postgres type translation error on the system table's internal varchar columns. Parameterized INSERTs crashed the server. And DELETEs were blocked because the postgres user lacks the required SUPER privilege — in our setup, the auto-created root@localhost superuser was not usable through the Postgres client path we were testing.

The docs show branch permissions working, but the examples use port 3306 (MySQL) and --user=root (a dolt server flag). These appear to be inherited from the dolt docs and not fully ported to doltgres yet. Doltgres describes itself as beta software, so this may improve.

Use Doltgres for branching, not for branch permissions yet. Route each agent to its assigned branch in the connection string, and treat authorization as an application-level concern.

But do we even need branch permissions? The orchestrator assigns each agent its branch, and the agent connects directly to it. The database gives you write isolation through branches. Your code gives you authorization through routing. For both RL (where the harness controls everything) and for a product app (where an agent works alongside you), this is enough.

Branch permissions become necessary when you want the database itself to block a misbehaving client from writing to the wrong branch. That matters in multi-tenant SaaS or untrusted environments. In a controlled research setup or a coding assistant, convention works because you control the code paths.

The deeper principle: the unit of attribution should match the unit of isolation. If two actors share a branch under the same user, you lose both isolation and attribution. The commit log shows "postgres wrote X" but not which actor caused it. The clean model:

  • RL: one branch per rollout or per worker. The branch name is the attribution. Single user is fine because you only care about what changed, not who (there's only one agent).
  • Multi-agent: one branch per agent, separate users. You get isolation from branches and attribution from the user in dolt_log. If agents need to collaborate, use a scenario branch that forks into worker branches, then merge back.
  • Human + agent: two users on separate branches. The human works on main, the agent works on a dev branch. Merging is the review step. Attribution in the log tells you which changes came from the agent vs the human.

If you truly need multiple actors on one branch, treat Doltgres as only the state store and put attribution in your own application layer: every write records actor_id, run_id, step_id in an audit table. Dolt history tells you what changed, your audit layer tells you who caused it.

II.fdolt CLI vs doltgres

They are separate binaries from separate repos:

  • doltgres (dolthub/doltgresql) — server only, Postgres wire protocol, no CLI subcommands. Version control is done in SQL: SELECT dolt_branch(), SELECT dolt_commit(), etc.
  • dolt (dolthub/dolt) — full CLI + server, MySQL wire protocol. Has dolt sql, dolt branch, dolt commit, etc.

Do not try to use the dolt CLI against doltgres data. They share the same engine underneath, but when we pointed dolt sql at a doltgres data directory it gave table has unknown fields — the on-disk representations are not interchangeable. The supported interface for doltgres is the Postgres wire protocol only.

If you want Postgres clients, use doltgres and do version control in SQL. If you want the Git-like CLI, use dolt instead.
