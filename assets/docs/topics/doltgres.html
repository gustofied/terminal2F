Doltgres

Doltgres is a Postgres-wire server built on the Dolt engine. It lets Postgres clients connect normally while exposing Dolt's version-control model through SQL. The core idea is Git for database state: you can branch, diff, merge, and commit database changes, with row-level history underneath. Every transaction can be turned into a versioned commit. An agent needs a safe copy of the world it is about to change, maybe not a sandbox,  perhaps not a container, but maybe a branch should work.

IWhy it matters for agents

There are two things, or more, but two interesting applications of Doltgres I see that is very interesting that include. 

  • RL: forkable state, fast reset, isolated concurrent worlds, diffable outcomes, replayability. The database as a training environment.
  • Product layer: human-readable versioned history, debugging, benchmarking, artifacts. The database as an auditable record.

Doltgres handles both because branching is cheap (no VMs, no containers, just a logical fork inside the same process) and the history is rich (row-level diffs, commit messages, per-row timelines). The primitive both layers share: a safe copy of the world before you change it.

II.aLearnings: server

The engine underneath is Dolt, which thinks in MySQL. Doltgres translates the Postgres wire protocol into that engine. Dolt docs and examples are MySQL-flavored, but the same concepts apply — you just adjust the syntax.

To see what configuration is available, run doltgres -config-help. This prints the full config.yaml reference:

yaml 
log_level: info                          # debug | info | warn | error

encode_logged_query: false               # encode SQL in logs (binary safety)

behavior:
  read_only: false                       # reject all writes if true
  dolt_transaction_commit: false         # auto dolt_commit on every tx

user:
  name: postgres
  password: password

listener:
  host: localhost
  port: 5432
  read_timeout_millis: 28800000          # 8 hours
  write_timeout_millis: 28800000         # 8 hours
  allow_cleartext_passwords: false

data_dir: ~/doltgres/databases            # where databases live on disk

cfg_dir: .doltcfg
privilege_file: .doltcfg/privileges.db   # user privileges
auth_file: .doltcfg/auth.db              # authentication data
branch_control_file: .doltcfg/branch_control.db  # branch permissions

The interesting ones for agents:

  • dolt_transaction_commit - when true, every SQL transaction automatically becomes a Dolt commit. Agents don't need to call dolt_commit() explicitly. Can also be set per-session via SET dolt_transaction_commit = 1; so only that connection auto-versions, not every admin query.
  • branch_control_file - branch-level permissions. Restrict which agents can write to which branches.
  • read_only - give agents read-only access to main while they write to their own branch on a separate connection.

II.bLearnings: commits

A transaction is a group of operations that either all succeed or all fail - all or nothing. Without transactions, if an error occurs mid-way, the database could end up in an inconsistent state. This is atomicity, the A in ACID.

In normal databases, "commit" only means finalizing a transaction. There's no standalone concept of committing outside of that.

Inside a transaction, each INSERT, SELECT, UPDATE, DELETE is a statement. Statements are the verbs. Tables are the nouns. Schemas define the shape of the nouns. The hierarchy:


text 
Transaction
  └── Statement  (INSERT INTO employees ...)
  └── Statement  (UPDATE accounts SET ...)
  └── Statement  (SELECT * FROM ...)
  └── COMMIT or ROLLBACK

Dolt adds a layer on top. A Dolt commit is a permanent versioned snapshot - like a git commit. It has a hash, a message, an author, a timestamp. You can go back to it, diff against it, branch from it. It lives forever in dolt_log. Multiple database transactions can happen between Dolt commits:

text 
Dolt commit  (versioned snapshot: hash, message, author)
  └── Transaction
  │     └── Statement
  │     └── Statement
  │     └── COMMIT
  └── Transaction
  │     └── Statement
  │     └── COMMIT
  └── dolt_commit('-am', 'description')

The bridge between the two: dolt_transaction_commit = 1. When set, every database transaction COMMIT also creates a Dolt commit. Without it, you can commit hundreds of database transactions and Dolt sees nothing - the data changes, but there is no versioned history. You would have to manually call dolt_commit() to snapshot.

When you call conn.execute("INSERT ...") in psycopg, you are just running a SQL statement. But the database always works in transactions - there is no way around it. With autocommit = True, every statement is silently wrapped in its own BEGIN/COMMIT. With autocommit off (the default), psycopg opens a transaction on the first statement and holds it open until you explicitly call conn.commit() or conn.rollback(). This means you can batch related writes and commit them as one unit - and with dolt_transaction_commit = 1, that whole batch becomes a single Dolt commit instead of N separate ones.

The dolt_transaction_commit setting controls whether Dolt automatically snapshots on every transaction commit:

false (default) - manual snapshots

text 
INSERT  →  tx commits  →  data changes ✓  →  dolt history: nothing
INSERT  →  tx commits  →  data changes ✓  →  dolt history: nothing
SELECT dolt_commit('-am', 'msg')           →  dolt history: one commit (both inserts)

You control when to snapshot. Good for admin work - keep the log clean, write meaningful commit messages.

true - automatic snapshots

text 
INSERT  →  tx commits  →  data changes ✓  →  dolt history: commit
INSERT  →  tx commits  →  data changes ✓  →  dolt history: commit

Every transaction commit creates a Dolt commit. Nothing slips through. Good for agent connections where you want full tracking. The tradeoff: the log gets noisy and commit messages are auto-generated, not meaningful.

Note: both the global config and per-session SET dolt_transaction_commit = 1 attribute commits to Dolt System Account, not the connected user. If you need attribution (who did what), use explicit dolt_commit('-Am', 'message') instead — that preserves the connected user's identity in the log.

II.cMulti-user

Multi-user works with standard Postgres statements. The config.yaml user block defines the initial server admin account — that's separate from Postgres roles you create after connecting. Once connected as admin, plain CREATE USER and GRANT work in a single connection:

python 
conn = psycopg.connect("host=127.0.0.1 user=postgres password=password dbname=getting_started")
conn.autocommit = True
conn.execute("CREATE USER agent1 WITH PASSWORD 'agent1pass'")
conn.execute("GRANT ALL ON DATABASE getting_started TO agent1")
conn.execute("GRANT ALL ON SCHEMA public TO agent1")
conn.execute("GRANT ALL ON ALL TABLES IN SCHEMA public TO agent1")
conn.close()

Users persist across server restarts in privileges.db. No need to recreate them each time — check if the user can login before creating.

Why separate users matter: attribution. When a user calls dolt_commit(), their name appears in dolt_log. Two agents sharing the postgres account means every commit says "postgres" and you lose track of who did what. With separate users you get git-blame for your database:

text 
commit_hash | committer | message
------------+-----------+------------------------
vs871...    | agent2    | agent2: add Bob Jones
okvul...    | agent1    | agent1: add Alice Smith
3pj0u...   | postgres  | create persons table

One caveat: attribution only works with explicit dolt_commit(). The auto-commit path (dolt_transaction_commit) attributes all commits to Dolt System Account regardless of which user made the change. For attribution, use manual commits.

When you need it: multi-agent setups, or human + agent workflows where you want to distinguish who made which changes. Single-agent RL with reset loops: one user is fine.

II.dBranches and isolation

Branches give each agent its own isolated copy of the database. Creating branches is a SQL operation:

sql 
SELECT dolt_branch('dev1', 'main');
SELECT dolt_branch('dev2', 'main');

The cleanest way to connect an agent to its branch: put the branch name directly in the connection string. No dolt_checkout() needed.

python 
# agent1 connects directly to dev1 branch
a1 = psycopg.connect(
    "host=127.0.0.1 user=agent1@localhost password=agent1pass "
    "dbname=getting_started/dev1"
)
a1.autocommit = True

# agent2 connects directly to dev2 branch
a2 = psycopg.connect(
    "host=127.0.0.1 user=agent2@localhost password=agent2pass "
    "dbname=getting_started/dev2"
)
a2.autocommit = True

Each branch behaves like its own writable database. Agent1 creates tables and inserts data on dev1, agent2 does the same on dev2, and main stays clean. Merging is a separate privileged operation your orchestrator does when the work looks good:

sql 
-- from main, merge agent1's work
SELECT dolt_merge('dev1');

This is the Cursor/PR model for databases: agents work on their branch, merging to main is a review step. The agent doesn't need permission to merge because merging isn't in its toolkit.

Merge works cleanly. When main has no divergent changes, it's a fast-forward — main's pointer moves to the branch's latest commit, and the agent's attribution is preserved in the log. After merging dev1, main's dolt_log shows agent1 as the committer for the rows that came from dev1.

Reset from seed

For RL or repeated agent runs, you need to reset a branch to a known state. The simplest way: delete the branch and recreate it from the seed:

There are two kinds of reset depending on what you want:

python 
# reset to current promoted state (main after merges)
conn.execute("SELECT dolt_branch('-D', 'dev1')")
conn.execute("SELECT dolt_branch('dev1', 'main')")

# reset to original seed (fixed commit hash)
conn.execute("SELECT dolt_branch('-D', 'dev1')")
conn.execute("SELECT dolt_branch('dev1', 's39nf5nm...')")

The difference matters. Recreating from main gives you whatever main looks like now — if you've merged agent work into it, the new branch starts from the promoted world. Recreating from a saved commit hash gives you the original seed state every time, regardless of what happened to main since.

For RL, you want the seed hash. Save it once after setting up the initial world (SELECT commit_hash FROM dolt_log LIMIT 1), then fork from that for every rollout. The agent gets a clean copy of the starting state, does its run, and you either merge the result or discard the branch. No containers, no snapshots — just a logical fork inside the same process.

Concurrency

Multiple agents can work in parallel on separate branches without issues. Initial test: 4 workers on 4 branches, each inserting 10 rows and committing — done in ~0.13s.

Scaled test: 40 concurrent rollouts structured as 10 examples × 4 rollouts each. Each example has its own seed state (a unique starting row), and the 4 rollouts fork from that shared seed. Each rollout gets its own Postgres user and branch. 40 workers ran in parallel, each inserting 10 rows and committing. All 40 finished in ~1.4s with full verification:

  • Each branch has exactly 11 rows (1 seed + 10 writes)
  • All 4 rollouts per example inherited the same seed row
  • No data leaked between examples
  • Each commit attributed to its own user (agent_e3_r2 etc.)
  • Main stayed untouched
text 
example0 seed → e0_r0, e0_r1, e0_r2, e0_r3
example1 seed → e1_r0, e1_r1, e1_r2, e1_r3
...
example9 seed → e9_r0, e9_r1, e9_r2, e9_r3

40 users, 40 branches, 400 inserts, 40 commits → 1.4s

Benchmarking

The script times the parallel section with time.time() around the thread pool. To quantify doltgres overhead more precisely, measure each phase separately:

python 
t_setup = time.time()
# create users + branches
t_setup = time.time() - t_setup

t_work = time.time()
# run all workers in parallel
t_work = time.time() - t_work

t_verify = time.time()
# read back and check
t_verify = time.time() - t_verify

print(f"setup: {t_setup:.2f}s  work: {t_work:.2f}s  verify: {t_verify:.2f}s")

Useful things to vary when benchmarking: number of concurrent workers, rows per worker, number of commits per worker (one big commit vs. many small ones), and table complexity (more columns, indexes). This lets you find where doltgres's overhead shows up relative to vanilla Postgres — the branch/commit machinery is the interesting cost, not the raw insert speed.

The validated lifecycle:

text 
seed commit → fork N branches → parallel agent work → commit
  → inspect → merge or discard → reset from seed

What this proves (and what it doesn't)

The 40-rollout test proves parallel isolated-world concurrency: many agents working on separate branches from shared seeds, with no data leaks and correct attribution. This is exactly the RL-style case — many independent rollouts from the same starting state.

What it does not test: multiple writers on the same branch, merge storms back into one branch, or conflict-heavy workloads. For the RL thesis those matter less — the isolated-world case is the one that counts.

The next question is not "does the model work?" but "does it hold up over time?" — specifically, what happens when you create and destroy thousands of branches across many steps. The right experiment for that is a multi-step epoch loop:

  • 10 seeds, 4 rollouts each
  • Repeat for N steps (100, 1000, ...)
  • Each step: create 40 branches, run 40 workers, delete branches
  • Track elapsed time per step — does branch churn degrade?
  • This gets closer to the real "200k branches over time" question

Orchestrator pattern

The natural shape for an agent environment manager: a single orchestrator (connected as postgres) that owns the lifecycle. It saves the seed hash, creates branches, hands each agent a connection string to its branch, waits for results, then decides to merge or discard. The agents never touch main, never create branches, never merge — they just connect, write, commit.

text 
Orchestrator (postgres)
  ├── save seed hash
  ├── create branch "run-42-agent1" from seed
  ├── create branch "run-42-agent2" from seed
  ├── hand off connection strings to agents
  ├── wait for agents to finish
  ├── inspect: dolt_diff, dolt_log per branch
  ├── merge good results into main (or a results branch)
  └── delete agent branches (or keep for replay)

Agent (agent1, agent2)
  ├── connect to assigned branch
  ├── read state, do work, write results
  ├── dolt_commit with meaningful message
  └── disconnect

This separates concerns cleanly. The orchestrator controls the experiment. The agents are stateless workers that see a database and write to it. Attribution comes from the user, isolation comes from the branch, and the orchestrator decides what gets promoted.

II.eBranch permissions

Dolt has a branch permissions system via two system tables: dolt_branch_control (who can write to which branches) and dolt_branch_namespace_control (who can create which branch names). The idea is straightforward — restrict agent1 to dev1:

sql 
INSERT INTO dolt_branch_control VALUES ('%', 'dev1', 'agent1', '%', 'write');

We could not get this to work through the Postgres wire protocol (doltgres 0.55.5). The system table columns are defined as MySQL types (VARCHAR(16383) COLLATE utf8mb4_0900_ai_ci) internally, and doltgres's query analyzer rejects any INSERT into columns that aren't Postgres-native types. The docs show branch permissions working, but the examples use port 3306 (MySQL protocol) and --user=root, which suggests they haven't been fully ported to the Postgres path yet. DoltHub confirmed the feature should work — it's a bug, not a missing feature. We filed an issue and they're working on a fix. Same error affects both dolt_branch_control and dolt_branch_namespace_control.

In practice, you don't need branch permissions for most setups. If I'm editing on main and an agent is working alongside me, I give it a separate branch and a separate user. The agent connects directly to its branch via the connection string. When its work looks good, I merge it in. With a different user, dolt_log shows who committed what regardless.

Where branch permissions would matter: multiple agents looking at the same database where one should only read (an evaluator agent checking state) while another writes. Without branch permissions, the read-only agent could still write if it wanted to. You can work around this by giving the evaluator a branched copy to read from, or by using Postgres GRANT/REVOKE to restrict table-level writes — but database-level branch enforcement would be cleaner.

The deeper principle: the unit of attribution should match the unit of isolation. If two actors share a branch under the same user, you lose both isolation and attribution. The commit log shows "postgres wrote X" but not which actor caused it. The clean model:

  • RL: one branch per rollout or per worker. The branch name is the attribution. Single user is fine because you only care about what changed, not who (there's only one agent).
  • Multi-agent: one branch per agent, separate users. You get isolation from branches and attribution from the user in dolt_log. If agents need to collaborate, use a scenario branch that forks into worker branches, then merge back.
  • Human + agent: two users on separate branches. The human works on main, the agent works on a dev branch. Merging is the review step. Attribution in the log tells you which changes came from the agent vs the human.

If you truly need multiple actors on one branch, treat Doltgres as only the state store and put attribution in your own application layer: every write records actor_id, run_id, step_id in an audit table. Dolt history tells you what changed, your audit layer tells you who caused it.

II.fdolt CLI vs doltgres

They are separate binaries from separate repos:

  • doltgres (dolthub/doltgresql) — server only, Postgres wire protocol, no CLI subcommands. Version control is done in SQL: SELECT dolt_branch(), SELECT dolt_commit(), etc.
  • dolt (dolthub/dolt) — full CLI + server, MySQL wire protocol. Has dolt sql, dolt branch, dolt commit, etc.

Do not try to use the dolt CLI against doltgres data. They share the same engine underneath, but when we pointed dolt sql at a doltgres data directory it gave table has unknown fields — the on-disk representations are not interchangeable. The supported interface for doltgres is the Postgres wire protocol only.

If you want Postgres clients, use doltgres and do version control in SQL. If you want the Git-like CLI, use dolt instead.

II.gBackups

Branches are not backups. They are pointers inside the same local storage — if the disk dies, everything dies: main, branches, all of it. A backup means copying data somewhere else.

Doltgres supports three approaches:

  • Block device snapshots (e.g. AWS EBS) — safest, works while the server is running. Recommended for production.
  • Push to remote (dolt_push to S3, DoltHub, GCS, or a file path) — only backs up committed data on the pushed branch, not the working set.
  • File copy — only safe if the server is fully stopped. Risk of inconsistent state otherwise.

For RL workloads this is mostly not relevant. Rollout branches are ephemeral — they live and die within a training run. What you might want to archive afterward are seeds and promoted results, and those can be pushed to a remote or exported to a separate results database. The thousands of throwaway rollout branches don't need backing up.

II.hGarbage collection

Doltgres stores data in a prolly tree of chunks on disk. When you write rows without committing, or delete a branch that had unique data, the old chunks stay on disk but nothing references them. That is garbage — wasted disk space, not data corruption.

Example: insert Alice, then update to Bob, then commit. The commit points to the Bob chunks. The Alice chunks are orphaned on disk. Same thing when you delete a rollout branch — its unique chunks become unreferenced.

Committed data is always safe. dolt_gc() only removes unreferenced chunks — anything pointed to by a commit stays.

sql 
SELECT dolt_gc();

For RL workloads, garbage accumulates from two places: intermediate writes before each dolt_commit(), and deleted rollout branches after each batch. Over thousands of epochs this can bloat the disk. Run GC periodically — after each learning example (one row of seeds with its rollouts), or every N epochs, depending on how long GC takes relative to the actual work.
