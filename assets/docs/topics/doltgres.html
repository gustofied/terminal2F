Doltgres

Doltgres is a Postgres-wire server built on the Dolt engine. It lets Postgres clients connect normally while exposing Dolt's version-control model through SQL. The core idea is Git for database state: you can branch, diff, merge, and commit database changes, with row-level history underneath. Every transaction can be turned into a versioned commit. An agent needs a safe copy of the world it is about to change, maybe not a sandbox,  perhaps not a container, but maybe a branch should work. Doltgres is currently in pre-alpha, heard they talked about proper release late 2026, nice! It has the same storage engine as Dolt

IWhy it matters for agents

There are two things, or more, but two interesting applications of Doltgres I see that is very interesting that include. 

  • RL: forkable state, fast reset, isolated concurrent worlds, diffable outcomes, replayability. The database as a training environment.
  • Product layer: human-readable versioned history, debugging, benchmarking, artifacts. The database as an auditable record.

Doltgres handles both because branching is cheap (no VMs, no containers, just a logical fork inside the same process) and the history is rich (row-level diffs, commit messages, per-row timelines). The primitive both layers share: a safe copy of the world before you change it.

aInstallation

Download doltgres from the releases page, unpack it, and put the doltgres binary on your PATH. Or use the install script:

bash 
curl -L https://github.com/dolthub/doltgresql/releases/latest/download/install.sh | sudo bash

We wrap this in a Python helper (setup_doltgres.py) that skips if already installed:

python 
import shutil, subprocess, requests

def is_installed():
    return shutil.which("doltgres") is not None

def install():
    if is_installed():
        print("doltgres already installed")
    else:
        r = requests.get(
            "https://github.com/dolthub/doltgresql/releases/latest/download/install.sh"
        )
        r.raise_for_status()
        subprocess.run(["sudo", "bash", "-c", r.text], check=True)

After installing, start the server by typing doltgres. It listens on port 5432 by default. standard Postgres port. I have this setup because I'm going to, we are going to use, or I am using it when you think about environments and sandboxing, not sandboxing. Then you need to be able to download binaries on nodes or remotes. Maybe even in a container, if you're going to also have a calling agent in the future, or MCP fast MCP. That's right.

Alternatively, if you don't have sudo or want the binary in your project directory, you can download and unpack it yourself:

python 
import platform, subprocess, os

def install_local(dest="."):
    if os.path.exists(f"{dest}/doltgres"):
        return
    system = "darwin" if platform.system() == "Darwin" else "linux"
    arch = "arm64" if platform.machine() == "arm64" else "amd64"
    tarball = f"doltgresql-{system}-{arch}.tar.gz"
    url = f"https://github.com/dolthub/doltgresql/releases/latest/download/{tarball}"
    subprocess.run(["curl", "-fsSL", "-o", tarball, url], check=True)
    subprocess.run(["tar", "-xzf", tarball], check=True)
    os.rename(f"doltgresql-{system}-{arch}/bin/doltgres", f"{dest}/doltgres")
    os.remove(tarball)
    subprocess.run(["rm", "-rf", f"doltgresql-{system}-{arch}"])

No sudo, no PATH. The binary lands in your project folder. Run with ./doltgres.

Doltgres looks for config.yaml in the current working directory. If you run scripts from a different folder, it won't find it. Use --config with Path(__file__).parent so the script always resolves the config relative to itself. But that only solves finding the config file. The paths inside the config (data_dir, cfg_dir) also resolve relative to cwd, not relative to the config file. So you also need to os.chdir into the script's directory before starting the server, otherwise data and .doltcfg end up wherever you happened to run from:

python 
import os
from pathlib import Path

DIR = Path(__file__).parent

# config.yaml paths (data_dir, cfg_dir) resolve relative to cwd,
# so we chdir to the script's folder before starting the server.
os.chdir(DIR)
subprocess.Popen(["doltgres", "--config", str(DIR / "config.yaml")])

bServer configuration

The engine underneath is Dolt, which thinks in MySQL. Doltgres translates the Postgres wire protocol into that engine. Dolt docs and examples are MySQL-flavored, but the same concepts apply, you can just adjust the syntax. Also doltgres has docs supplied here, some things might be lacking but we are as we know in beta.

To see what configuration is available, run doltgres -config-help. This prints the full config.yaml reference:

yaml 
log_level: info                          # debug | info | warn | error

encode_logged_query: false               # encode SQL in logs (binary safety)

behavior:
  read_only: false                       # reject all writes if true
  dolt_transaction_commit: false         # auto dolt_commit on every tx

user:
  name: postgres
  password: password

listener:
  host: localhost
  port: 5432
  read_timeout_millis: 28800000          # 8 hours
  write_timeout_millis: 28800000         # 8 hours
  allow_cleartext_passwords: false

data_dir: ~/doltgres/databases            # where databases live on disk

cfg_dir: .doltcfg
privilege_file: .doltcfg/privileges.db   # user privileges
auth_file: .doltcfg/auth.db              # authentication data
branch_control_file: .doltcfg/branch_control.db  # branch permissions

The interesting ones for agents:

  • dolt_transaction_commit - when true, every SQL transaction automatically becomes a Dolt commit. There is no need to call dolt_commit() explicitly. Can also be set per-session via SET dolt_transaction_commit = 1; so only that connection auto-versions, not every admin query per example.
  • branch_control_file - branch-level permissions. Restrict who can write to which branches.
  • read_only - give read-only access to main while they write to their own branch on a separate connection.

cCommits

A transaction is a group of operations that either all succeed or all fail - all or nothing. Without transactions, if an error occurs mid-way, the database could end up in an inconsistent state. This is atomicity, the A in ACID.

In normal databases, "commit" only means finalizing a transaction. There's no standalone concept of committing outside of that.

Inside a transaction, each INSERT, SELECT, UPDATE, DELETE is a statement. Statements are the verbs. Tables are the nouns. Schemas define the shape of the nouns. The hierarchy:


text 
Transaction
  └── Statement  (INSERT INTO employees ...)
  └── Statement  (UPDATE accounts SET ...)
  └── Statement  (SELECT * FROM ...)
  └── COMMIT or ROLLBACK

Dolt adds a layer on top. A Dolt commit is a permanent versioned snapshot - like a git commit. It has a hash, a message, an author, a timestamp. You can go back to it, diff against it, branch from it. It lives forever in dolt_log. Multiple database transactions can happen between Dolt commits:

text 
Dolt commit  (versioned snapshot: hash, message, author)
  └── Transaction
  │     └── Statement
  │     └── Statement
  │     └── COMMIT
  └── Transaction
  │     └── Statement
  │     └── COMMIT
  └── dolt_commit('-am', 'description')

The bridge between the two: dolt_transaction_commit = 1. When set, every database transaction COMMIT also creates a Dolt commit. Without it, you can commit hundreds of database transactions and Dolt sees nothing, the data changes, but there is no versioned history. You would have to manually call dolt_commit() to snapshot. Doe it has to be said, that using dolt_transaction_commit = 1 will not attribute it to the user/role who did it.

When you call conn.execute("INSERT ...") in psycopg, you are just running a SQL statement. But the database always works in transactions - there is no way around it. With autocommit = True, every statement is silently wrapped in its own BEGIN/COMMIT. With autocommit off (the default), psycopg opens a transaction on the first statement and holds it open until you explicitly call conn.commit() or conn.rollback(). This means you can batch related writes and commit them as one unit - and with dolt_transaction_commit = 1, that whole batch becomes a single Dolt commit instead of N separate ones.

The dolt_transaction_commit setting controls whether Dolt automatically snapshots on every transaction commit:

false (default) - manual snapshots

text 
INSERT  →  tx commits  →  data changes ✓  →  dolt history: nothing
INSERT  →  tx commits  →  data changes ✓  →  dolt history: nothing
SELECT dolt_commit('-am', 'msg')           →  dolt history: one commit (both inserts)

You control when to snapshot. Good for admin work - keep the log clean, write meaningful commit messages.

true - automatic snapshots

text 
INSERT  →  tx commits  →  data changes ✓  →  dolt history: commit
INSERT  →  tx commits  →  data changes ✓  →  dolt history: commit

Every transaction commit creates a Dolt commit. Nothing slips through. Good for agent connections where you want full tracking. The tradeoff: the log gets noisy and commit messages are auto-generated, not meaningful.

Note: both the global config and per-session SET dolt_transaction_commit = 1 attribute commits to Dolt System Account, not the connected user. If you need attribution (who did what), use explicit dolt_commit('-Am', 'message') instead, that preserves the connected user's identity in the log.

One thing to understand: dolt_commit does not commit a specific transaction. It snapshots the current state of the working set, like git commit. If five INSERTs happened across five transactions and nobody called dolt_commit in between, one dolt_commit captures all five. SQL transactions and Dolt commits are independent layers. You decide when to snapshot. That's it for commit so far.

eBranches and isolation

A branch is a copy of the database state. You can create as many as you want, and anyone can connect to any branch. Creating branches is a SQL operation:

sql 
SELECT dolt_branch('dev1', 'main');
SELECT dolt_branch('dev2', 'main');

A clean way to connect a user to its branch: put the branch name directly in the connection string. No dolt_checkout() needed.

python 
# alice connects directly to dev1 branch
a1 = psycopg.connect(
    "host=127.0.0.1 user=alice password=alice123 "
    "dbname=getting_started/dev1"
)
a1.autocommit = True

# bob connects directly to dev2 branch
a2 = psycopg.connect(
    "host=127.0.0.1 user=bob password=bob123 "
    "dbname=getting_started/dev2"
)
a2.autocommit = True

Branch permissions

Dolt has a branch permissions system via two system tables: dolt_branch_control (who can write to which branches) and dolt_branch_namespace_control (who can create which branch names). The idea is straightforward, restrict alice to dev1:

sql 
INSERT INTO dolt_branch_control VALUES ('%', 'dev1', 'alice', '%', 'write');

We could not get this to work through the Postgres wire protocol (doltgres 0.55.5). The system table columns are defined as MySQL types (VARCHAR(16383) COLLATE utf8mb4_0900_ai_ci) internally, and doltgres's query analyzer rejects any INSERT into columns that aren't Postgres-native types. The docs show branch permissions working, but the examples use port 3306 (MySQL protocol) and --user=root, which suggests they haven't been fully ported to the Postgres path yet. DoltHub confirmed the feature should work, it's a bug, not a missing feature. We filed an issue and they're working on a fix. Same error affects both dolt_branch_control and dolt_branch_namespace_control.

In practice, you don't need branch permissions for most setups. If I'm editing on main and a user is working alongside me, I give it a separate branch and a separate user. The user connects directly to its branch via the connection string. When its work looks good, I merge it in. With a different user, dolt_log shows who committed what regardless.

Where branch permissions would matter: multiple users looking at the same database where one should only read (an evaluator checking state) while another writes. Without branch permissions, the read-only user could still write if it wanted to. You can work around this by giving the evaluator a branched copy to read from, or by using Postgres GRANT/REVOKE to restrict table-level writes, but database-level branch enforcement would be cleaner.


Well they seems, to have fixed it with doltgres 0.55.6, so let's try it again once more. It works. dolt_branch_control has five columns: database, branch, user, host, and permissions. On a fresh database it comes pre-populated with a wildcard row (%, %, %, %, 2) that grants everyone write access to all branches, plus auto-generated rows for any connection that touched a branch. To enforce permissions, clear the table first, then insert only the rules you want:
sql 
-- clear defaults
DELETE FROM dolt_branch_control;

-- alice can only write to dev1, bob can only write to dev2
INSERT INTO dolt_branch_control VALUES ('%', 'dev1', 'alice', '%', 'write');
INSERT INTO dolt_branch_control VALUES ('%', 'dev2', 'bob', '%', 'write');

After this, alice writing to dev2 gets: `alice`@`127.0.0.1` does not have the correct permissions on branch `dev2`. Only the superuser can modify dolt_branch_control, regular roles cannot change their own permissions. The permissions column takes three values:

  • admin: grants all permissions, plus write access to the system tables for matching database + branch entries.
  • write: grants ability to write on the branch and modify it (rename, delete, etc.).
  • read: does not grant anything extra, reading a branch is an irrevocable right for all users. This exists for visual convenience versus an empty field.

By default the wildcard row grants everyone write access to all branches, as we saw. All users, even those without an entry at all, still have read access to all branches. Permissions only affect modifying branches and writing to the system tables. The two system tables work in opposite ways: dolt_branch_control starts with a wildcard row allowing everything, you remove it and add specific rules to lock down. dolt_branch_namespace_control starts empty, which means anyone can create any branch name. Adding rules there restricts who can create which branch names.

The branch column supports % wildcards, so you can grant access to multiple branches at once. For example, if the orchestrator creates rollout branches like run-42-alice, run-43-alice, run-44-alice, you don't need a row per branch. One rule covers all of them:

sql 
INSERT INTO dolt_branch_control VALUES ('%', 'run-%-alice', 'alice', '%', 'write');

Alice can now write to any branch matching run-%-alice but not to run-%-bob or main. This scales nicely for the RL case where you spin up hundreds of rollout branches per user, you set one permission rule per user and the orchestrator creates branches freely within that pattern.  Need to thinker on that.


superuser controls the table, and the permissions are real enforcement.

The second table, dolt_branch_namespace_control, controls who can create branches with which names. It has four columns: database, branch, user, host (no permissions column). When the table is empty, anyone can create any branch. Adding a row like ('%', 'run-%-alice', 'alice', '%') means only alice can create branches matching that pattern. When someone creates a branch, doltgres auto-adds a row in dolt_branch_control giving the creator admin permission on that branch. That's where the auto-generated rows we saw earlier came from. For the orchestrator pattern this is less relevant since the orchestrator (postgres) creates all branches and workers just connect to the ones they're given.

sql 
-- only alice can create branches starting with "alice-"
INSERT INTO dolt_branch_namespace_control VALUES ('%', 'alice-%', 'alice', '%');

-- alice can do this
SELECT dolt_branch('alice-experiment');  -- works

-- bob cannot
SELECT dolt_branch('alice-experiment');  -- error: cannot create branch named `alice-experiment`

Cursor/PR model

Each branch behaves like its own writable database. Alice creates tables and inserts data on dev1, bob does the same on dev2, and main stays clean. Merging is a separate privileged operation your orchestrator does when the work looks good:

sql 
-- from main, merge alice's work
SELECT dolt_merge('dev1');

This is the Cursor/PR model for databases: users work on their branch, merging to main is a review step. With dolt_branch_control you can enforce this, give the user write access only to its branch, and only the orchestrator (postgres) can merge into main.

Merge works cleanly. When main has no divergent changes, it is a fast-forward, main's pointer moves to the branch's latest commit, and the user's attribution is preserved in the log. After merging dev1, main's dolt_log shows alice as the committer for the rows that came from dev1.

The deeper principle: the unit of attribution should match the unit of isolation. If two actors share a branch under the same user, you lose both isolation and attribution. The commit log shows "postgres wrote X" but not which actor caused it. The clean model:

  • RL: one branch per rollout or per worker. The branch name is the attribution. Single user is fine because you only care about what changed, not who (there's only one worker). Use dolt_branch_control to lock workers to their branches.
  • Multi-user: one branch per user, separate roles. You get isolation from branches and attribution from the user in dolt_log. Branch permissions enforce who writes where. If users need to collaborate, use a scenario branch that forks into worker branches, then merge back.
  • Human + user: two users on separate branches. The human works on main, the other user works on a dev branch. Branch permissions restrict the user to its branch. Merging is the review step. Attribution in the log tells you which changes came from which user.

If you truly need multiple actors on one branch, use dolt_branch_control to grant each actor write access to that branch. Each actor gets its own role, so dolt_log still shows who committed what. The branch is shared but attribution is preserved through separate users. And when merged, dolt_log on main still shows who committed each change.

Reset from seed

For RL or repeated runs, you need to reset a branch to a known state. The simplest way: delete the branch and recreate it from the seed:

There are two kinds of reset depending on what you want:

python 
# reset to current promoted state (main after merges)
conn.execute("SELECT dolt_branch('-D', 'dev1')")
conn.execute("SELECT dolt_branch('dev1', 'main')")

# reset to original seed (fixed commit hash)
conn.execute("SELECT dolt_branch('-D', 'dev1')")
conn.execute("SELECT dolt_branch('dev1', 's39nf5nm...')")

The difference matters. Recreating from main gives you whatever main looks like now, if you've merged work into it, the new branch starts from the promoted world. Recreating from a saved commit hash gives you the original seed state every time, regardless of what happened to main since.

For RL, you want the seed hash. Save it once after setting up the initial world (SELECT commit_hash FROM dolt_log LIMIT 1), then fork from that for every rollout. The user gets a clean copy of the starting state, does its run, and you either merge the result or discard the branch. No containers, no snapshots, just a logical fork inside the same process.

fBackups

Branches are not backups. They are pointers inside the same local storage, if the disk dies, everything dies: main, branches, all of it. A backup means copying data somewhere else.

Doltgres supports three approaches:

  • Block device snapshots (e.g. AWS EBS), safest, works while the server is running. Recommended for production.
  • Push to remote (dolt_push to S3, DoltHub, GCS, or a file path), only backs up committed data on the pushed branch, not the working set.
  • File copy, only safe if the server is fully stopped. Risk of inconsistent state otherwise.

For RL workloads this is mostly not relevant. Rollout branches are ephemeral, they live and die within a training run. What you might want to archive afterward are seeds and promoted results, and those can be pushed to a remote or exported to a separate results database. The thousands of throwaway rollout branches don't need backing up.

gGarbage collection

Doltgres stores data in a prolly tree of chunks on disk. When you write rows without committing, or delete a branch that had unique data, the old chunks stay on disk but nothing references them. That is garbage, wasted disk space, not data corruption.

Example: insert Alice, then update to Bob, then commit. The commit points to the Bob chunks. The Alice chunks are orphaned on disk. Same thing when you delete a rollout branch, its unique chunks become unreferenced.

Committed data is always safe. dolt_gc() only removes unreferenced chunks, anything pointed to by a commit stays.

sql 
SELECT dolt_gc();

For RL workloads, garbage accumulates from two places: intermediate writes before each dolt_commit(), and deleted rollout branches after each batch. Over thousands of epochs this can bloat the disk. Run GC periodically, after each learning example (one row of seeds with its rollouts), or every N epochs, depending on how long GC takes relative to the actual work.

One thing to watch: avoid random primary keys (UUIDs, random ints). Doltgres stores data in a prolly tree, and random keys scatter inserts across the entire tree instead of clustering them. This causes more chunks to be rewritten on every insert, which means more garbage and more disk usage. Sequential IDs are better for doltgres's structural sharing.

hReplication

Doltgres supports two replication modes: remote-based (push/pull through a shared remote like S3 or DoltHub) and direct-to-standby (primary pushes all writes to standby servers for high availability). Both replicate between doltgres instances.

The more interesting case: doltgres can be a read-replica of a regular Postgres server. As it consumes changes from the primary, it creates dolt commits, giving you versioned history on top of production data. This opens up a workflow where you replicate a real Postgres database into doltgres, then branch from that realistic state for rollouts. Each rollout forks from real-world data instead of mock seeds, without ever touching production.

Replicas can also offload the main server. If hundreds of rollout workers are all reading seed state from one doltgres instance, that's a bottleneck. Spread the read load across replicas and let the primary handle commits and merges.

iMetrics

Doltgres can optionally expose metrics through a Prometheus HTTP endpoint. Enable it by defining a metrics section in your YAML configuration. In our config it runs on localhost:11228. This gives you query latency, connection counts, and other server stats out of the box. Doltgres consumes CPU, memory, and disk. Consuming more of any of these resources than the host has available can lead to degraded performance. Use your system's built-in resource monitoring to inspect doltgres's usage of these resources. For query-level debugging, set log_level: debug or trace in config.yaml. This logs every query, its result, and latency to the terminal where doltgres is running.

Memory-wise, doltgres needs at minimum 2GB RAM, 4GB for larger workloads, 8GB for production. Usage grows with database size, concurrent connections, and query complexity. Important when picking nodes GPU instances, make sure the machine has enough headroom for both doltgres and whatever else is running. Another thing: under too much concurrent load, doltgres can consume all CPU on a host. Doltgres is CPU-bound so it competes with other CPU work,  if reads saturate the CPU, spin up read-replicas on cheap CPU-only nodes and load balance across them. Writes are a different story: doltgres serializes all writes, so it caps around ~300 writes/second. More writers means more latency piling up. For RL rollouts this is fine since each worker does a few inserts and one commit, but worth knowing if you scale up.

A config enabling metrics on port 11228:

yaml 
metrics:
  labels: {}
  host: localhost
  port: 11228

The endpoint at /metrics exposes doltgres-specific metrics (prefixed dss_) and Go runtime metrics (prefixed go_). The useful ones:

  • dss_concurrent_connections: clients currently connected
  • dss_concurrent_queries: queries currently running
  • dss_query_duration_bucket: histogram of query latencies
  • dss_is_replica: whether this server is a replica (only with replication enabled)
  • dss_replication_lag: replication lag in ms (only with replication enabled)
  • go_memstats_alloc_bytes: memory currently allocated
  • go_gc_duration_seconds: histogram of GC pause durations
  • go_gc_duration_seconds_count: total seconds spent on garbage collection

Scrape with Prometheus, Datadog, or any compatible tool by pointing it at localhost:11228/metrics. We will use this endpoint to build our dashboard and tooling.

IIIDashboard, testing, and stress testing

At this point I am no longer really "learning Doltgres basics." I am moving into building a small evaluation framework around it. So it's time to look at some tooling for testing, dashboard testing, stress testing and more.

aLab setup

The tooling lives in dolt/tooling/ with a clean separation: server.py handles doltgres lifecycle (install, start, fresh start, terminate), utils.py has formatting and metrics helpers, and lab.py is the workspace for experimenting.

The lab starts a fresh doltgres instance, creates a database and a table, sets up users with permissions, and commits the base schema. From that base commit it creates N "world" snapshots, each a slightly different starting state committed and saved as a hash. The key insight: a commit hash in dolt is a full database snapshot. You can branch from any hash later without copying data, the branch just points at that snapshot.

python 
# create world snapshots from the base schema
for w in range(num_worlds):
    dolt_reset('--hard', base_hash)   # rewind to empty table
    INSERT INTO world VALUES (...)    # insert world-specific seed data
    dolt_commit('-Am', 'world N')     # commit the snapshot
    save hash                         # this hash = this world's state

# reset main back to clean base
dolt_reset('--hard', base_hash)

Later, branching from a world hash gives you that world's state as your starting point. No data duplication, just a pointer.

bConcurrency

Multiple users can work in parallel on separate branches without issues. Initial test: 4 workers on 4 branches, each inserting 10 rows and committing, done in ~0.13s.

Scaled test: 40 concurrent rollouts structured as 10 examples × 4 rollouts each. Each example has its own seed state (a unique starting row), and the 4 rollouts fork from that shared seed. Each rollout gets its own Postgres user and branch. 40 workers ran in parallel, each inserting 10 rows and committing. All 40 finished in ~1.4s with full verification:

  • Each branch has exactly 11 rows (1 seed + 10 writes)
  • All 4 rollouts per example inherited the same seed row
  • No data leaked between examples
  • Each commit attributed to its own user (user_e3_r2 etc.)
  • Main stayed untouched
text 
example0 seed → e0_r0, e0_r1, e0_r2, e0_r3
example1 seed → e1_r0, e1_r1, e1_r2, e1_r3
...
example9 seed → e9_r0, e9_r1, e9_r2, e9_r3

40 users, 40 branches, 400 inserts, 40 commits → 1.4s

cBenchmarking

The script times the parallel section with time.time() around the thread pool. To quantify doltgres overhead more precisely, measure each phase separately:

python 
t_setup = time.time()
# create users + branches
t_setup = time.time() - t_setup

t_work = time.time()
# run all workers in parallel
t_work = time.time() - t_work

t_verify = time.time()
# read back and check
t_verify = time.time() - t_verify

print(f"setup: {t_setup:.2f}s  work: {t_work:.2f}s  verify: {t_verify:.2f}s")

Useful things to vary when benchmarking: number of concurrent workers, rows per worker, number of commits per worker (one big commit vs. many small ones), and table complexity (more columns, indexes). This lets you find where doltgres's overhead shows up relative to vanilla Postgres, the branch/commit machinery is the interesting cost, not the raw insert speed.

The validated lifecycle:

text 
seed commit → fork N branches → parallel user work → commit
  → inspect → merge or discard → reset from seed

dWhat this proves (and what it doesn't)

The 40-rollout test proves parallel isolated-world concurrency: many users working on separate branches from shared seeds, with no data leaks and correct attribution. This is exactly the RL-style case, many independent rollouts from the same starting state.

What it does not test: multiple writers on the same branch, merge storms back into one branch, or conflict-heavy workloads. For the RL thesis those matter less, the isolated-world case is the one that counts.

The next question is not "does the model work?" but "does it hold up over time?", specifically, what happens when you create and destroy thousands of branches across many steps. The right experiment for that is a multi-step epoch loop:

  • 10 seeds, 4 rollouts each
  • Repeat for N steps (100, 1000, ...)
  • Each step: create 40 branches, run 40 workers, delete branches
  • Track elapsed time per step, does branch churn degrade?
  • This gets closer to the real "200k branches over time" question

eOrchestrator pattern

The natural shape for an environment manager: a single orchestrator (connected as postgres) that owns the lifecycle. It saves the seed hash, creates branches, hands each user a connection string to its branch, waits for results, then decides to merge or discard. The users never touch main, never create branches, never merge, they just connect, write, commit.

text 
Orchestrator (postgres)
  ├── save seed hash
  ├── create branch "run-42-alice" from seed
  ├── create branch "run-42-bob" from seed
  ├── hand off connection strings to users
  ├── wait for users to finish
  ├── inspect: dolt_diff, dolt_log per branch
  ├── merge good results into main (or a results branch)
  └── delete user branches (or keep for replay)

User (alice, bob)
  ├── connect to assigned branch
  ├── read state, do work, write results
  ├── dolt_commit with meaningful message
  └── disconnect

This separates concerns cleanly. The orchestrator controls the experiment. The users are stateless workers that see a database and write to it. Attribution comes from the user, isolation comes from the branch, and the orchestrator decides what gets promoted.
